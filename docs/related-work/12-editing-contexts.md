# Editing Contexts, Working Sets, and Concurrent Uncommitted Edits

**Status:** Sourced 2026-08-19, opened alongside `../design/13-editing-context.md`; extended the same day after the design conversation named Jujutsu and IntelliJ changelists as targets and reframed the optimization claim. Core citations verified against publisher records; items still on recall are tagged.

## Why this theme

`../design/13-editing-context.md` proposes an **editing context**: a named collection of definitions a user or agent is simultaneously viewing and editing, whose members update live without an explicit commit gate, and which scopes migration. None of the existing eleven themes covers it. `02-structure-editors.md` covers how you edit *one* program; `04-incrementality.md` covers what gets recomputed; `05-naming-versioning.md` covers how versions relate; `09-scid.md` covers the image tradition and ENVY. The **working set as a first-class object** falls between all of them.

Five literatures answer five separable parts of the claim, and they disagree with each other in useful ways:

- **Curated working sets** (HCI/IDE) — the set is a thing the user arranges.
- **Inferred working sets** (HCI/IDE) — the set is a degree-of-interest function the system computes from interaction.
- **Concurrent uncommitted edits** (VCS/IDE) — several unrelated edits in flight at once over one workspace, each committable independently.
- **When unrelated edits commute** (PL theory) — the formal question underneath the previous bullet.
- **Live feedback without a commit step** (live programming) — evaluating continuously against context-supplied inputs, which is what `13`'s optimization claim actually turns out to be about.

## Concurrent uncommitted edits — the named targets

- **IntelliJ IDEA changelists.** [Group changes into changelists](https://www.jetbrains.com/help/idea/managing-changelists.html), [Changelist conflicts](https://www.jetbrains.com/help/idea/settings-version-control-changelist-conflicts.html). `[not peer-reviewed — product documentation]` **[Priority read for this theme.]** Several named sets of uncommitted changes over **one** working copy, each committable independently, with **exactly one active** at a time — new modifications land in the active list by default. Changes can be split *within a single file* across lists. The mechanism worth stealing is **changelist conflict detection**: editing a file belonging to an *inactive* changelist raises a *Resolve Changelist Conflict* dialog offering four resolutions — shelve, move to active, switch active, or ignore — plus persistent visual marking ("a yellow stripe on top of a file from an inactive changelist," filenames red in tabs and the project view). That is a shipped, evaluated answer to `13`'s axis 8 (what does a user see when contexts overlap?) and to the UX question raised about the opacity/working-set correspondence. Ancestry: Perforce **pending changelists**, which are server-side and named — the same idea with the workspace stored remotely.
- **Jujutsu (`jj`).** [docs.jj-vcs.dev](http://docs.jj-vcs.dev/latest/working-copy/), glossary. **Now read in source — `../systems/jj/`, pinned to `253d3be`.** `[not peer-reviewed — software]` **[Priority read for this theme.]** Four ideas, each directly on point:
  - **The working copy *is* a commit** (`@`), and *"Jujutsu will automatically create commits from the working-copy contents when they have changed."* There is no staging area and no commit gate; every command snapshots first. This is the mechanism behind "live-update many things without an explicit commit step" — the commit stops being a gate and becomes a continuously-maintained object.
  - **Workspaces** — *"You can have multiple working copies backed by a single repo"* (`jj workspace add`), with **staleness** as the coordination primitive: a workspace whose working-copy commit was modified elsewhere becomes stale and is repaired by `jj workspace update-stale`. Many contexts over one store, with a defined interference story.
  - **Change ID vs commit ID** — a change ID *"tracks a commit as it evolves through rewrites,"* while the commit ID identifies each specific version. This is **exactly** arbor's mint/thread axis (p11, `../design/10-minted-identity.md`), arrived at independently and shipped. A change with more than one visible commit is *divergent* — a named, tolerated state rather than an error.
  - **The operation log** — *"the DAG formed by operation objects, much in the same way that commits form a DAG"* — a second history axis over the repo itself, which is what makes "you can't lose work by making a mistake" true. arbor-core's `H` is the same shape one layer down (bindings rather than operations).
  - **Revsets** — *"a functional language for selecting a set of revisions."* The precedent for making context membership a **query** rather than an extensional set, which dissolves `13`'s curated-vs-derived dichotomy rather than choosing a side.
- **GitButler** — [gitbutler.com](https://gitbutler.com/). `[not peer-reviewed — software]` *"Works with multiple virtual branches simultaneously, first-class conflicts, and operations history"* (jj's own `docs/related-work.md`). IntelliJ changelists taken to their conclusion: the concurrent uncommitted edits are not sets of files but **branches**, live at once over one working directory. The closest existing thing to `../design/13-editing-context.md`'s many-contexts-at-once requirement in a mainstream tool. Unread.
- **Gitless** — [gitless.com](https://gitless.com/). `[not peer-reviewed — software]` A simplified Git interface with **no index/staging area**, and which does not move working-copy changes between branches. Useful as the minimal statement of "remove the commit gate" without also making the working copy a commit.
- **Smalltalk change sets** (Squeak/Pharo), and **ENVY/Developer** editions — `09-scid.md`. `[not peer-reviewed — software]` A change set is a *named collection of changes to the live image*, accumulated as you edit, with no commit gate at all: the image is already changed. The oldest form of "the working set is where the edits live," and the one closest to arbor's Smalltalk north star.
- **git's index, `stash`, `add -p`, and worktrees.** `[not peer-reviewed — software]` The degenerate cases, useful as a lower bound: the index is *one* unnamed staging set, `stash` is a stack of anonymous ones, and worktrees give a whole second checkout per concurrent edit (the pattern `08-agentic-vc.md` records as the de facto agent isolation primitive, with the standing critique that it is "only low-level workspace isolation").

## When do unrelated edits commute — the theory

The formal content under "concurrent unrelated edits." Relevant because arbor will eventually want to say *why* two contexts touching disjoint parts of the store cannot interfere.

- **Samuel Mimram & Cinzia Di Giusto (MFPS 2013) — "A Categorical Theory of Patches."** ENTCS 298, 283–307. DOI [10.1016/j.entcs.2013.09.018](https://doi.org/10.1016/j.entcs.2013.09.018). `[verified]` Merging as a **pushout** in a category whose objects are files and whose arrows are patches; independent patches are exactly those with a pushout. The theoretical basis Pijul cites for itself.
- **Carlo Angiuli, Edward Morehouse, Daniel R. Licata, Robert Harper (ICFP 2014) — "Homotopical Patch Theory."** DOI [10.1145/2628136.2628158](https://doi.org/10.1145/2628136.2628158). `[verified]` Patch theory in homotopy type theory: repositories as a type, patches as paths, and *patch laws as higher paths*, with the merge algorithm falling out of the elaboration. The most formally serious treatment of "two edits are independent" available, and the natural neighbour for an arbor formalism that wants a theorem about non-interfering contexts.
- **Darcs patch theory** ([darcs.net/Theory](https://darcs.net/Theory/GaneshPatchAlgebra)) and **Pijul** ([pijul.org/model](https://pijul.org/model/)). `[not peer-reviewed — software + informal notes]` The implementations. Darcs' primitives are **commutation** and **inversion**, with dependencies declared per patch; Pijul rebuilds it on Mimram–Di Giusto to fix Darcs' soundness and performance problems. Pijul also makes **conflicts first-class values in the store** rather than markers in a file — the same move jj makes, and one arbor gets for free if a broken migration is *a context* rather than a failure.

## Curated working sets

- **Andrew Bragdon, Robert Zeleznik, Steven P. Reiss, Suman Karumuri, William Cheung, Joshua Kaplan, Christopher Coleman, Ferdi Adeputra, Joseph J. LaViola Jr. (CHI 2010) — "Code Bubbles: A Working Set-Based Interface for Code Understanding and Maintenance."** DOI [10.1145/1753326.1753706](https://doi.org/10.1145/1753326.1753706). `[verified]` **[Priority read for this theme.]** The strongest statement anywhere that the unit of an IDE should be a *working set of fragments*, not a set of files: function-sized, editable, concurrently visible, savable, shareable. Companion: **Bragdon et al. (ICSE 2010) — "Code Bubbles: Rethinking the User Interface Paradigm of Integrated Development Environments,"** DOI [10.1145/1806799.1806866](https://doi.org/10.1145/1806799.1806866). `[verified]` Note the granularity: arbor's store is *already* fragment-granular, so what Code Bubbles builds an interface to simulate, arbor has natively.
- **Austin Z. Henley & Scott D. Fleming (CHI 2014) — "The Patchworks Code Editor: Toward Faster Navigation with Less Code Arranging and Fewer Navigation Mistakes."** DOI [10.1145/2556288.2557073](https://doi.org/10.1145/2556288.2557073). `[verified]` The direct rebuttal to Code Bubbles: a **fixed patch grid plus a ribbon** instead of a free canvas, on the argument that *arranging* the working set is itself a cost — evaluated against both Eclipse and Code Bubbles. Read the two together; the disagreement is the finding. Follow-up: **Henley, Fleming et al. (CHI 2017) — "Toward Principles for the Design of Navigation Affordances in Code Editors,"** DOI [10.1145/3025453.3025645](https://doi.org/10.1145/3025453.3025645). `[verified — secondary]`
- **David Röthlisberger, Oscar Nierstrasz, Stéphane Ducasse, Alexandre Bergel (WCRE 2009) — "Autumn Leaves: Curing the Window Plague in IDEs."** `[UNVERIFIED — check before citing]` Degree-of-interest applied to *closing* editors automatically. The eviction half of the problem, which the curated literature mostly ignores and which `13` has to answer: when does something leave a context?

## Inferred working sets

- **Mik Kersten & Gail C. Murphy (AOSD 2005) — "Mylar: A Degree-of-Interest Model for IDEs."** DOI [10.1145/1052898.1052912](https://doi.org/10.1145/1052898.1052912). `[verified — secondary]` **[Priority read for this theme.]** The **task context**: a degree-of-interest value per program element, raised by interaction and decayed over time, used to filter and rank every view in the IDE. The alternative to explicit membership, requiring no bookkeeping from the user.
- **Mik Kersten & Gail C. Murphy (FSE 2006) — "Using Task Context to Improve Programmer Productivity."** SIGSOFT '06/FSE-14, 1–11. DOI [10.1145/1181775.1181777](https://doi.org/10.1145/1181775.1181777). `[verified]` The evaluation, and the reason this line matters rather than merely existing: task contexts are *captured, modeled, and persisted*, and industry programmers using them showed a statistically significant productivity improvement. Shipped as **Mylyn**.
- **George W. Furnas (CHI 1986) — "Generalized Fisheye Views."** DOI [10.1145/22627.22342](https://doi.org/10.1145/22627.22342). `[UNVERIFIED — check before citing]` The ancestor: degree of interest = a priori importance minus distance from the focus.

## Live feedback without a commit step

This section exists because the design conversation reframed `13`'s optimization claim. It is **not** "cache what is hot." It is: *the context supplies the evaluation environment — including which inputs, at what size — so live feedback is computed against context-bound data rather than production data.* A 5-row sample instead of a 5-petabyte dataset. That is a **binding** question, not a caching question, and it has its own literature.

- **Sorin Lerner (CHI 2020) — "Projection Boxes: On-the-fly Reconfigurable Visualization for Live Programming."** DOI [10.1145/3313831.3376494](https://doi.org/10.1145/3313831.3376494). `[verified]` **[Priority read for this theme.]** Start from the *full semantics* of the program, then use **projections** to pick the subset of runtime state to display — a framework that subsumes prior visualizations rather than adding one. The user study reports that always-on visualization is *not* found distracting, and that preference variation is wide enough to require configurability. Directly the "see live values update" half of `13`'s claim 1.
- **Sorin Lerner (UIST 2020) — "Focused Live Programming with Loop Seeds."** DOI [10.1145/3379337.3415834](https://doi.org/10.1145/3379337.3415834). `[verified]` **[Priority read for this theme.]** Names the **loop-datavoid problem**: live programming depends on test inputs to produce runtime values, and *"there are no test inputs that can drive certain incomplete loops to produce useful data"* because the useful data only appears once the loop is written. The response is a **seed** — a small, focused, user-supplied starting state that makes live evaluation tractable and meaningful. This is the closest published statement of "the editing context carries the small input you actually evaluate against," and it is the citation `13`'s claim 2 should be argued from rather than from Denning.
- **Hazel's live evaluation of incomplete programs** — `02-structure-editors.md`. The mechanism that makes "no explicit commit step" *safe*: a mistake in one term becomes a hole rather than a failure, so the rest of the context keeps evaluating. arbor's p8/p9 hole line is the same machinery.
- **Notebook computing and its empirical critiques** — `07-commons.md`. A notebook is an editing context with an execution order, and the critiques are largely critiques of *implicit, unreified* context — the failure mode `13` should design against.

## Workspaces as stored objects — databases

- **Randy H. Katz (ACM Computing Surveys 1990) — "Toward a Unified Framework for Version Modeling in Engineering Databases."** 22(4), 375–408. `[verified — secondary]` (DOI not confirmed; cite by volume/pages.) **[Priority read for this theme.]** Names the primitives `13` is reaching for: **check-out / check-in**, private vs. shared workspaces, version graphs, configurations, and change propagation across a *hierarchy* of workspaces. CAD databases faced arbor's problem — many designers, long-lived edits over a shared object graph, propagation scoped to a workspace — twenty-five years before agentic version control asked it again.
- **François Bancilhon, Won Kim, Henry F. Korth (VLDB 1985) — "A Model of CAD Transactions."** `[UNVERIFIED — check before citing]` The **long transaction**: an edit session lasting hours or days with a private workspace, unservable by conventional locking. The formal frame for "a context holds uncommitted work," and for why atomic-commit-over-the-whole-context is the wrong default.
- **H. T. Kung & John T. Robinson (ACM TODS 1981) — "On Optimistic Methods for Concurrency Control."** DOI [10.1145/319566.319567](https://doi.org/10.1145/319566.319567). `[UNVERIFIED — check before citing]` Validate-at-commit rather than lock-at-read — the posture `08-agentic-vc.md`'s STORM entry argues against and that arbor's immutability makes cheap.

## Workspaces as stored objects — version control

- **Rachel Potvin & Josh Levenberg (CACM 2016) — "Why Google Stores Billions of Lines of Code in a Single Repository."** 59(7), 78–87. DOI [10.1145/2854146](https://doi.org/10.1145/2854146). `[verified]` **[Priority read for this theme.]** Describes **CitC (Clients in the Cloud)**: workspaces stored *server-side*, named, shareable, and browsable by other people and by tools, holding only the delta against a snapshot. The "stored, named, many, shareable" answer to `13`'s axes 1 and 3 at the largest scale anyone has tried it.
- **Meta's Sapling + EdenFS** ([sapling-scm.com](https://sapling-scm.com)); **Microsoft's VFS for Git / Scalar**; **git `sparse-checkout` and partial clone**. `[not peer-reviewed — software]` The industrial form of "materialize only what is checked out, fetch the rest on demand." Real evidence, but at *file* granularity and *repository* scale — which is the caveat, since arbor's granularity is a definition.

## The locality argument, and why it is the weaker one

- **Peter J. Denning (CACM 1968) — "The Working Set Model for Program Behavior."** 11(5), 323–333. DOI [10.1145/363095.363141](https://doi.org/10.1145/363095.363141). `[verified]` The origin of the term and of the argument's *shape*: define the working set as the pages referenced in a recent window, **measure** that references are local, then allocate to the working set. Follow-up: **Denning (IEEE TSE 1980) — "Working Sets Past and Present."** `[UNVERIFIED — check before citing]`

Denning is the right citation for a **caching** claim ("prefetch and retain what the context touches") and the wrong one for the claim `13` actually makes after the reframe, which is about *which inputs are bound*, not which results are retained. Kept here because the caching claim may still be made later, and because Denning's discipline — measure locality before designing for it — is the bar either version has to meet.

## Where it plugs in

- `../design/13-editing-context.md` — the whole document. Changelists and jj answer the concurrent-edits axis; Code Bubbles vs. Patchworks splits curated-vs-arranged; Mylyn is the inferred alternative; jj revsets suggest membership-as-query; Lerner's loop seeds are what the optimization claim should be argued from; Katz and CitC answer stored-and-named.
- `../design/04-naming-layer.md:130-137` — the update-strategy **scope** axis. A context is a candidate value for it; Katz's propagation-across-workspaces is the prior art for what that means formally.
- `../design/10-minted-identity.md` and p11's threads — **jj's change ID is arbor's mint thread, shipped.** Its *divergent change* state (one change ID, several visible commits, labeled rather than rejected) is a directly usable answer to the mint-stability-under-merge question at `../design/open-questions.md`.
- `formalism/paper/arbor-core.tex` — `H` and jj's operation log are the same shape one layer apart. If contexts land, the patch-theory pair (Mimram–Di Giusto, Angiuli et al.) is where a non-interference theorem for disjoint contexts would come from.
- `formalism/paper/arbor-stlc.tex` — the **residual**. Unison delivers it as a scratch buffer; Katz delivers it as cross-workspace propagation; Pijul and jj make conflicts first-class values. Three precedents for "the residual is an object, not an error."

## Gaps and negative findings

- **No formal treatment of a working set as an object in a program store.** Katz formalizes workspaces over engineering databases; patch theory formalizes independence of *changes*, not membership of a *view*. Nothing found does either over a content-addressed definition store.
- **No published evaluation of working-set-scoped optimization at definition granularity.** The file-granularity evidence (CitC, EdenFS, sparse checkout) is strong and industrial; nothing found tests whether it survives the granularity shrink.
- **Curated vs. inferred appears unresolved.** Code Bubbles and Patchworks disagree; Mylyn's inferred model shipped, was evaluated positively, and is now largely dormant. No direct comparison found — and jj's revsets suggest the dichotomy may be the wrong frame.
- **Nothing found on editing contexts for non-human agents.** `08-agentic-vc.md` covers worktree isolation and STORM's mediated workspace; neither treats the agent's working set as an object with these properties.
- **jj and IntelliJ changelists have no publications.** Like Unison, they are artifacts. jj at least has substantial written design documentation; changelists have only product docs. Both belong in `../systems/` if they are ever leaned on hard.
- **Verification is partial.** Six items remain `[UNVERIFIED]`: Autumn Leaves, Furnas, Bancilhon et al., Kung & Robinson, Denning 1980, and Katz's DOI (the citation itself is confirmed via bibliographies).
