# SCID — "Source Code In Database," and What It Actually Is

**Status:** Index. Sourced 2026-08-03. Annotations are notes and observations, not substrate policy — see `00-index.md` §"How to read this".

## Why this theme, and the headline finding

**SCID is not an academic literature.** A dedicated search found **zero peer-reviewed papers using "SCID" or "source code in database" as a term of art.** In the indexed literature "SCID" resolves to Severe Combined Immunodeficiency, the Structured Clinical Interview for DSM, and Shane's Chess Information Database. What exists under the name is one hobbyist essay, one c2-wiki thread, one notability-flagged Wikipedia stub, and a scattering of blog posts.

The *idea* has a real and deep citable ancestry — but under other names: relational views of programs, syntax-directed environments, residential/image-based systems, code-as-facts databases, and projectional editing. Those are the citations.

And the idea has a *current* research programme, also under another name: **"substrates."** Jonathan Edwards, Tomas Petricek, and Robert Hirschfeld organized **Substrates 2025** at ‹Programming› 2025 (Prague, June 2025), by invitation, on 2–4 page vision statements. Edwards' own vision statement lists **"database-based substrates"** and **"static typing viability"** as open problems. That is the conversation arbor should join, and the name to use — not SCID.

## The SCID term itself

- **Roedy Green — "SCID: Source Code In Database."** Canadian Mind Products, c. 1996–2017. [mindprod.com/project/scid.html](https://mindprod.com/project/scid.html). `[not peer-reviewed — personal essay]` The origin of the term as used online. Argues source should be pre-parsed and stored as an interlinked parse-tree/token-object database, with text as one of many *projections* (hide comments, show only loop structure, render expressions mathematically); global rename becomes trivial because a name exists in exactly one place and everything else is a pointer. Cites IBM VisualAge Java, Eclipse, Smalltalk, Logo, Fowler's language workbenches, and Bell Labs' SeeSoft. The closest thing to a "core SCID text," and it is a hobbyist essay.
- **c2 wiki — "SourceCodeInDatabase,"** thread dated 12 January 2007. [wiki.c2.com/?SourceCodeInDatabase](http://wiki.c2.com/?SourceCodeInDatabase). `[not peer-reviewed — wiki]` The plain URL returns a JS loading shim; the readable source is `http://c2.com/wiki/remodel/pages/SourceCodeInDatabase`. Sources Green's essay explicitly. Contains the canonical objection — "clarity, longevity and flexibility of plain text source" — plus a sketch DB schema and worries about broken metadata links. Related pages: `PowerOfPlainText`, `TableOrientedProgramming`, `FileSystemAlternatives`.
- **Wikipedia — "Source code in database."** [en.wikipedia.org](https://en.wikipedia.org/wiki/Source_code_in_database). `[not peer-reviewed — stub; notability-flagged since January 2021]` Two paragraphs. Its only citation is CodeOntology. Names IBM VisualAge Java as the exemplar and notes the central practical objection: unparseable code cannot be ingested. Useful only as evidence of the term's marginal status — and note that its one "modern SCID example" is a semantic-web derived index, not a primary store.
- **Malte Skarupke (2014) — "Ideas for a Programming Language Part 1: Source Code in Database."** *Probably Dance*, 6 December 2014. [probablydance.com](https://probablydance.com/2014/12/06/ideas-for-a-programming-language-part-1-source-code-in-database/). `[not peer-reviewed — blog]` **The best-argued modern practitioner statement.** Tooling quality dominates language choice; DB storage eliminates redundant parsing and gives every tool full semantic information with no cold-start or sync problem. That last point is the explicit argument for a **primary** rather than **derived** database — the axis that separates arbor from Kythe, Glean, CodeQL, and every other system in this file's third section.

## The real ancestry: programs are not text

- **Mark A. Linton (SDE 1984) — "Implementing Relational Views of Programs."** ACM SIGSOFT/SIGPLAN Software Engineering Symposium on Practical Software Development Environments, May 1984, pp. 132–140. `[verified — citation confirmed; full text not fetched]` **[Priority read — the one peer-reviewed citation for the SCID thesis.]** A program stored as relations in a relational DBMS, with source text as a *view*. If arbor cites one paper for "code in a database," it is this one rather than the wiki.
- **Tim Teitelbaum & Thomas Reps (CACM 1981) — "The Cornell Program Synthesizer."** DOI [10.1145/358746.358755](https://doi.org/10.1145/358746.358755). `[verified]` "Programs are not text; they are hierarchical compositions of computational structures." Fully annotated in `02-structure-editors.md`.
- **Warren Teitelman & Larry Masinter (IEEE Computer 1981) — "The Interlisp Programming Environment."** 14(4):25–33. DOI [10.1109/C-M.1981.220410](https://doi.org/10.1109/C-M.1981.220410). `[verified]` The residential tradition: code lives in the image, edited by a structure editor, with the environment — not files — as the source of truth.
- **Masterscope** — Interlisp's program-analysis database, with an English-like query language, cross-references kept current, and system-wide changes applied through the structure editor. **The direct ancestor of Kythe, Glean, and CodeQL.** Documented in manuals and Xerox newsletters (e.g. bitsavers `Masterscope_1-01_Feb85.pdf`), **not in a peer-reviewed paper.** `[not peer-reviewed — primary-source documentation]`
- **Warren Teitelman (IEEE Software 1984) — "A Tour Through Cedar."** 1(2):44–73. [PDF](https://www.cs.tufts.edu/comp/150FP/archive/warren-teitelman/tour-cedar.pdf). `[verified]` The other half of the PARC lineage: Cedar/Mesa integrated-but-compiled, against Interlisp-D's residential model.
- **Adele Goldberg (1984) — *Smalltalk-80: The Interactive Programming Environment.*** Addison-Wesley (the "red book"). `[verified — book]` The image tradition: the snapshot *is* the program store; there are no source files in the deployment sense. Relevant as the existence proof that a whole-system persistent store works — and as the counterexample on collaboration and deployment that Petricek & Edwards explicitly set out to fix.
- **Charles Rich & Richard C. Waters (IEEE Computer 1988) — "The Programmer's Apprentice: A Research Overview."** 21(11):10–25. [MIT DSpace](https://dspace.mit.edu/handle/1721.1/6054). Book version: *The Programmer's Apprentice*, ACM Press Frontier Series, 1990. `[verified]` Programs represented as *plans* — a semantic graph, not text — so an assistant can analyze, synthesize, and modify them; KBEmacs is the working prototype. **The earliest sustained argument that a structured store is what makes automated program manipulation possible** — the same argument now being re-run for LLM agents in `08-agentic-vc.md`.
- **Joseph Pelrine, Alan Knight, Adrian Cho (2001) — *Mastering ENVY/Developer.*** SIGS / Cambridge University Press, ISBN 0521666503. `[verified — book]` **No peer-reviewed paper exists for IBM VisualAge or ENVY/Developer.** ENVY stored Smalltalk code as versioned method and class objects in a shared team repository — **arguably the most successful production SCID system ever shipped**, and immutably versioned *per method*, which is close to arbor's per-definition granularity. Everything else about VisualAge's file-less workspace is product documentation and folklore.
- **Also in this lineage, unverified:** "Damokles — A database system for software engineering environments" (Dittrich et al., Springer 1986) and Steven Reiss, "Simplifying data integration: the design of the Desert software development environment" (ICSE 1996). Also unverified: the authorship of "Interlisp-D: Further Steps in the Flight from Time-Sharing" (commonly credited to Beau Sheil). `[UNVERIFIED — check before citing]`

## Code as facts in a database — the query line

All of these are **derived indices over files, not primary stores.** That distinction is the crux, and Skarupke's blog post is the only place the survey found it argued explicitly.

- **Elnar Hajiyev, Mathieu Verbaere, Oege de Moor (ECOOP 2006) — "codeQuest: Scalable Source Code Queries with Datalog."** LNCS 4067, pp. 2–27. DOI [10.1007/11785477_2](https://doi.org/10.1007/11785477_2). `[verified]` **ECOOP 2006, not ICSE 2006.** Safe Datalog over a relational encoding of program structure, compiled to SQL. The demonstration that a code database with a declarative query language beats hand-rolled AST traversal.
- **Pavel Avgustinov, Oege de Moor, Michael Peyton Jones, Max Schäfer (ECOOP 2016) — "QL: Object-oriented Queries on Relational Data."** LIPIcs 56, pp. 2:1–2:25. DOI [10.4230/LIPIcs.ECOOP.2016.2](https://doi.org/10.4230/LIPIcs.ECOOP.2016.2). `[verified]` **The proper archival citation for .QL / Semmle / CodeQL** — classes as logical properties, subclassing as implication, virtual dispatch resolved logically, all compiled to Datalog. Cite this, not the Semmle Wikipedia page.
- **Oege de Moor, Mathieu Verbaere et al. (SCAM 2007, keynote) — ".QL for Source Code Analysis."** [PDF](https://codeql.github.com/publications/ql-for-source-code-analysis.pdf). `[verified]` The position statement of the code-as-database thesis from the industrial side.
- **Mattia Atzeni & Maurizio Atzori (ISWC 2017) — "CodeOntology: RDF-ization of Source Code."** LNCS 10588. DOI [10.1007/978-3-319-68204-4_2](https://doi.org/10.1007/978-3-319-68204-4_2). Companion demo: [CEUR-WS Vol-1963 paper543](https://ceur-ws.org/Vol-1963/paper543.pdf). `[verified]` Java source as RDF triples, SPARQL-queryable, with an OpenJDK 8 dataset.
- **Douglas A. Creager & Hendrik van Antwerpen (EVCS 2023) — "Stack Graphs: Name Resolution at Scale."** Eelco Visser Commemorative Symposium, OASIcs. DOI [10.4230/OASIcs.EVCS.2023.8](https://doi.org/10.4230/OASIcs.EVCS.2023.8). `[verified]` **[Priority read.]** GitHub's production system: name-binding information as graph structure where paths are valid bindings, **file-incremental** (each file yields an isolated subgraph, so unchanged files never need reanalysis), and purely syntactic — no build execution. **Structurally the closest published analogue to arbor's per-definition independence**, and the strongest evidence that independently-analyzable units scale. Compare with Zwaan et al.'s scope graphs in `04-incrementality.md`.
- **Glean (Meta).** [glean.software](https://glean.software/), [github.com/facebookincubator/Glean](https://github.com/facebookincubator/Glean), Meta engineering blog, 19 December 2024. `[not peer-reviewed — artifact; no paper exists]` Immutable schema-defined facts forming a DAG over RocksDB, with automatic dedup, queried in **Angle** (Datalog-like, currently non-recursive). Note: "a system for collecting, deriving and working with facts about source code" is the **repository tagline**, not a paper title.
- **Kythe (Google).** [kythe.io](https://kythe.io/). `[not peer-reviewed — artifact]` Docs and schema only; no paper, no author attribution on the site. Descends from an internal "Grok" (2008) — that lineage is oral history.
- **LSIF and SCIP.** [lsif.dev](https://lsif.dev/), [Sourcegraph on SCIP](https://sourcegraph.com/blog/announcing-scip). `[not peer-reviewed — specs]` LSIF is a Microsoft/LSP-adjacent JSON format for persisting language-server knowledge; SCIP is Sourcegraph's Protobuf successor with human-readable symbol IDs replacing monikers and resultSets.

## The current programme: substrates

- **Jonathan Edwards (2025) — "Substrates vision statement."** *Alarming Development*, 12 May 2025. [alarmingdevelopment.org/?p=1842](https://alarmingdevelopment.org/?p=1842). `[not peer-reviewed — blog post; a submission to the Substrates 2025 workshop]` **[Priority read — for the definition and the problem list.]** Defines a substrate as *"a complete and self-sufficient programming system, with a persistent code & data store, providing a direct-manipulation UI on that state,"* where "programming & using are on a spectrum, not distinct." His open-problem list explicitly includes **"database-based substrates"** and **"static typing viability."** The nearest thing to a current, named research agenda for what arbor is, and it names arbor's problem as open.
- **Substrates 2025** — ‹Programming› 2025, Prague, 2–6 June 2025. Organizers: Jonathan Edwards (independent), Robert Hirschfeld (HPI), Tomas Petricek (Charles University). [2025.programming-conference.org](https://2025.programming-conference.org/home/substrates-2025). `[verified as a venue]` By invitation, 2–4 page vision statements. **Gap: no accepted-submissions list was published on the site**, so the other vision statements could not be enumerated. `[UNVERIFIED]` **Likely the single richest untapped source for this theme — worth emailing the organizers.**
- **Petricek & Edwards (HATRA 2021) — "Typed Image-based Programming with Structure Editing."** arXiv:[2110.08993](https://arxiv.org/abs/2110.08993). `[verified]` **[Priority read.]** **The closest published statement of arbor's exact problem.** Image-based systems (Smalltalk, LISP, HyperCard, Flash, spreadsheets) avoid enormous stack complexity but lose collaboration and deployment; the fix is *types plus structure editing*, because structure editing captures type-definition changes with enough fidelity to migrate the persisted data automatically. That is `formalism/`'s "migration is a whole-store rewrite" question approached from the other direction.
- **Edwards & Petricek (2025/26) — "Baseline: Operation-Based Evolution and Versioning of Data."** arXiv:[2512.09762](https://arxiv.org/abs/2512.09762), December 2025 (rev. June 2026); to appear, *Programming Journal*. `[verified as preprint]` **[Priority read.]** Introduces **Operational Differencing**: versioning richly structured data by recording high-level operations *including refactorings and schema changes*, so branching is "just copying" and diffs and merges survive structural transformation. Queries are operationalized so they auto-adapt to schema change. **The closest existing work to arbor's edit calculus** (`formalism/paper/arbor-core.tex` §"Part V").
- **Petricek & Edwards (UIST 2025) — "Denicek: Computational Substrate for Document-Oriented End-User Programming."** DOI [10.1145/3746059.3747646](https://doi.org/10.1145/3746059.3747646). `[verified]`
- **Edwards, Petricek, van der Storm, Litt (2025) — "Schema Evolution in Interactive Programming Systems."** *Programming Journal* 9(1). DOI [10.22152/programming-journal.org/2025/9/2](https://doi.org/10.22152/programming-journal.org/2025/9/2); arXiv:2412.06269. `[verified]` Predecessor: **Edwards, Petricek, van der Storm (2023) — "Live & Local Schema Change: Challenge Problems,"** arXiv:2309.11406 `[verified]`.
- **Jakubovic, Edwards, Petricek (2023) — "Technical Dimensions of Programming Systems."** *Programming Journal* 7(3). DOI [10.22152/programming-journal.org/2023/7/13](https://doi.org/10.22152/programming-journal.org/2023/7/13). `[verified]` **The best available vocabulary for comparing substrates** — usable directly as an evaluation framework for arbor against Unison, Hazel, MPS, and Smalltalk.
- **Beckmann, Thiede, Lincke, Hirschfeld (2026) — "Hybrid Structured Editing: Structures for Tools, Text for Users."** *The Art, Science, and Engineering of Programming* 11(1), art. 1. arXiv:[2603.05644](https://arxiv.org/abs/2603.05644). `[verified]` **The strongest recent published counterargument** to storing only structure: an explicit hedge against the full projectional bet. Also listed in `02-structure-editors.md`.

## Sean McDirmid — adjacent, about liveness rather than storage

Verified via [dblp.org/pid/76/4167](https://dblp.org/pid/76/4167.html):

- **"Living it up with a live programming language."** OOPSLA 2007, pp. 623–638. DOI [10.1145/1297027.1297073](https://doi.org/10.1145/1297027.1297073). `[verified]`
- **"Coding at the speed of touch."** Onward! 2011, pp. 61–76. DOI [10.1145/2048237.2048246](https://doi.org/10.1145/2048237.2048246). `[verified]`
- **"Escaping the maze of twisty classes."** Onward! 2012, pp. 127–138. DOI [10.1145/2384592.2384605](https://doi.org/10.1145/2384592.2384605). `[verified]`
- **"Usable live programming."** Onward! 2013, pp. 53–62. DOI [10.1145/2509578.2509585](https://doi.org/10.1145/2509578.2509585). **Most Notable Paper Award 2023.** `[verified]`
- **McDirmid et al. — "It's alive! continuous feedback in UI programming."** PLDI 2013, pp. 95–104. DOI [10.1145/2491956.2462170](https://doi.org/10.1145/2491956.2462170). `[verified]`

**Honest assessment: McDirmid is only tangentially relevant to SCID.** His contribution is that editing and debugging should be concurrent, with execution *places* made navigable. He does not argue for database storage. Include him for the liveness prerequisite — a live environment needs an always-analyzed store — not as an SCID proponent. **Caution:** "The road to live programming" (ICSE 2018, DOI 10.1145/3180155.3180200) surfaces alongside his name but is probably Rein, Ramson, Lincke, Hirschfeld & Pape. `[UNVERIFIED]`

## Contemporary systems without publications

- **Darklang (Paul Biggar).** [The design of Dark](https://medium.com/darklang/the-design-of-dark-59f5d38e52d2) (blog); Changelog #430; Software Engineering Daily; Future of Coding ep. 43. `[not peer-reviewed — blog and interviews; no paper]` Language plus structured editor plus infrastructure, "deployless," syntax errors impossible. The most commercially serious recent attempt — and a cautionary tale: Dark publicly retreated from its structured editor.
- **Dolt / DoltHub.** [github.com/dolthub/dolt](https://github.com/dolthub/dolt), [dbdb.io/db/dolt](https://dbdb.io/db/dolt). `[not peer-reviewed — artifact; no paper or whitepaper]` Git-style version control at database scale, built on **Prolly Trees** — a probabilistic B-tree inherited from Attic Labs' **Noms**, and a content-addressed, structurally-shared data structure. Worth a sentence: Dolt shows structural sharing plus content addressing gives cheap branching for *data*; arbor claims the same for *code*.
- **Bhola, Krishnan, Kurmala, NS (2026) — "Code Isn't Memory: A Structural Codebase Index Inside a Coding Agent."** arXiv:[2606.22417](https://arxiv.org/abs/2606.22417), 21 June 2026. `[verified as preprint]` Evaluates a structural codebase index inside a coding agent on SWE-PolyBench Verified and SWE-bench Pro; reports a large localization gain, a statistically separated resolve gain, and lower cost per solve versus agentic-grep. Not framed as SCID, and it is a derived index rather than a store — but it is the current *empirical* evidence that structured representations beat text search for automated program manipulation. The Programmer's-Apprentice argument, with numbers. Cross-reference `08-agentic-vc.md`.

## Gaps and negative findings

- **SCID has no academic literature.** One essay, one wiki thread, one stub. Say so plainly rather than padding a bibliography that does not exist.
- **No 2020–2026 peer-reviewed paper frames itself as SCID or "code as data in a database"** in the primary-store sense. The self-identified programme is **substrates**.
- **"The Program Database" has no canonical paper.** In practice the phrase means Microsoft's PDB debug-symbol format. The genuine ancestors are Linton 1984, Masterscope, and the SE-database systems (Damokles, Desert).
- **Roslyn as academic work: refuted.** The only "papers" found were a ResearchGate preprint with inconsistent attribution and an IJSRA article — neither citable. "Compiler as a service" is product terminology.
- **IBM VisualAge has no peer-reviewed paper.** ENVY/Developer at least has the Pelrine/Knight/Cho book.
- **Kythe, Glean, LSIF, SCIP, Mergiraf, Dolt, Darklang: all artifacts without papers.** The Glean "title" that circulates is a repo tagline.
- **Substrates 2025's accepted submissions were never published.** The richest untapped source in this theme; worth an email.
- **Nobody has published the primary-store-vs-derived-index argument.** Skarupke's blog post is the best statement of it. That is a genuine gap and arbor sits on the unclaimed side.
