# Malleable Tooling — Moldable Development, Tailorable Systems, End-User Customization

**Status:** Index. Sourced 2026-08-06. Annotations are notes and observations, not substrate policy — see `00-index.md` §"How to read this".

## Why this theme

Themes 01–09 cover the store, the languages, the editing layer, and the surrounding social vision; none covers the **interface layer** — layer 4 of `../design/06-architecture.md` — beyond the editor itself. This file supplies that coverage, in three parts that answer one question from three directions: *who gets to shape the tools, and how cheaply?*

- **Moldable development** (Gîrba, Nierstrasz, Chiş; Glamorous Toolkit) — development tools should be shaped per-domain and per-question, with custom views cheap enough to build in minutes. The named, worked-out methodology for what arbor's aspect + interface layers gesture at: many small derived views over a live store.
- **Tailorable systems / end-user programming** — the older HCI lineage on letting users of a system modify it: EMACS, Xerox Buttons, the tailoring-level taxonomies, meta-design, and the end-user software engineering survey.
- **Malleable software** — the current wave (Webstrates, Varv, Wildcard, Ink & Switch), substrate-adjacent and largely out of the local-first cluster arbor already meets in `05-naming-versioning.md` (Peritext) and `06-multi-language.md` (Cambria).

One observation worth carrying forward (an observation, not policy): every moldable view in Glamorous Toolkit is molded over a **mutable image** — a view's result can be silently invalidated by any state change. A moldable view over arbor's store would be a derived aspect keyed by content hash (`../design/02-definitions-and-derived-data.md`) and would inherit eval-stability: never invalidated, cacheable, shareable across users. Moldable-tooling-over-an-immutable-store appears to be an unclaimed composition — a failure to find, not a proof of absence.

## Moldable development — the methodology

The corpus is one group's (SCG Bern / feenk), sustained over a decade. The methodology is real and citable; the flagship artifact is not (see the next section).

- **Chiş, Gîrba, Nierstrasz (SLE 2014) — "The Moldable Debugger: A Framework for Developing Domain-Specific Debuggers."** LNCS 8696, pp. 102–121. DOI [10.1007/978-3-319-11245-9_6](https://doi.org/10.1007/978-3-319-11245-9_6). Best Student Paper. `[verified]` The first moldable tool: debuggers adapted per-domain via pluggable extensions (custom views + actions) activated by context. Journal version: **Chiş, Denker, Gîrba, Nierstrasz — "Practical domain-specific debuggers using the Moldable Debugger framework,"** *Computer Languages, Systems & Structures* 44 (2015), pp. 89–113, DOI [10.1016/j.cl.2015.08.005](https://doi.org/10.1016/j.cl.2015.08.005) `[verified]` — note the journal version adds Denker.
- **Chiş, Nierstrasz, Syrel, Gîrba (Onward! 2015) — "The Moldable Inspector."** pp. 44–60. DOI [10.1145/2814228.2814234](https://doi.org/10.1145/2814228.2814234). `[verified]` Object inspection as multiple cheap domain-specific views per object — the closest single paper to "aspects rendered per-definition in the detail pane." Author order is Chiş–Nierstrasz–Syrel–Gîrba (Syrel is routinely dropped). Precursor at IWST 2014 `[verified — secondary]`; tool demo **"GTInspector: a moldable domain-aware object inspector,"** SPLASH 2015 Companion, pp. 15–16, DOI [10.1145/2814189.2814194](https://doi.org/10.1145/2814189.2814194) `[verified]`.
- **Chiş, Gîrba, Kubelka, Nierstrasz, Reichhart, Syrel (Onward! 2016) — "Moldable, Context-Aware Searching with Spotter."** pp. 128–144. DOI [10.1145/2986012.2986023](https://doi.org/10.1145/2986012.2986023). `[verified]` The third moldable tool: search. Same six authors: **"Exemplifying Moldable Development"** (PX/16 @ ECOOP 2016), pp. 33–42, DOI [10.1145/2984380.2984385](https://doi.org/10.1145/2984380.2984385) `[verified]` — the first paper using "moldable development" as a methodology name in a title — and the consolidated chapter **"Moldable Tools for Object-Oriented Development,"** *Present and Ulterior Software Engineering*, Springer 2017, pp. 77–101, DOI [10.1007/978-3-319-67425-4_6](https://doi.org/10.1007/978-3-319-67425-4_6) `[verified]`.
- **Andrei Chiş (2016) — *Moldable Tools.*** PhD thesis, University of Bern. [boris.unibe.ch/89072](https://boris.unibe.ch/89072/). `[verified — via DBLP; the Bern repository itself sits behind a bot wall]` The unifying statement: debugger, inspector, and search all moldable, adapted to domain context at low cost.
- **Nierstrasz & Gîrba (VISSOFT 2022) — "Making Systems Explainable."** pp. 1–4 (invited keynote paper). DOI [10.1109/VISSOFT55257.2022.00009](https://doi.org/10.1109/VISSOFT55257.2022.00009). `[verified]` The crispest short statement of the thesis: software should answer developers' questions through causally-connected custom tools rather than static documentation.
- **Nierstrasz & Gîrba (EuroPLoP 2024) — "Moldable Development Patterns."** pp. 18:1–18:14. DOI [10.1145/3698322.3698327](https://doi.org/10.1145/3698322.3698327); arXiv:[2409.18811](https://arxiv.org/abs/2409.18811). `[verified]` **[Priority read — the best long-form statement.]** A pattern catalog (Custom View, Custom Action, Custom Search, …) distilled from years of open-source and industrial application. **EuroPLoP, not PLoP** — the citation circulates wrong. Also the one citable hook for Lepiter, which it name-checks.
- **Chiş, Gîrba, Nierstrasz (Onward! 2024) — "Moldable Exceptions."** pp. 1–12. DOI [10.1145/3689492.3690044](https://doi.org/10.1145/3689492.3690044); arXiv:[2409.00465](https://arxiv.org/abs/2409.00465). `[verified]` A raised exception carries context that adapts the debugger's interface — the moldable idea pushed into the language runtime.
- **Chiş, Nierstrasz, Gîrba (PLATEAU @ SPLASH 2015) — "Towards Moldable Development Tools."** pp. 25–26. DOI [10.1145/2846680.2846684](https://doi.org/10.1145/2846680.2846684). `[verified]` The early two-page manifesto.
- **Nierstrasz, Ducasse, Gîrba (ESEC/FSE 2005) — "The Story of Moose: An Agile Reengineering Environment."** pp. 1–10 (invited). DOI [10.1145/1081706.1081707](https://doi.org/10.1145/1081706.1081707). `[verified]` The lineage: GT descends from the Moose analysis platform, and this retrospective is the original case for making analysis tooling cheap to customize.

## Glamorous Toolkit, Pharo, and uptake — the artifacts

- **Glamorous Toolkit (feenk).** [gtoolkit.com](https://gtoolkit.com/), [github.com/feenkcom/gtoolkit](https://github.com/feenkcom/gtoolkit). `[not peer-reviewed — software/artifact]` **No system paper on GT exists** — zero DBLP hits; its identity in the literature is carried entirely by the moldable-tools papers above plus ESUG demos. The same artifact-without-a-paper pattern as Unison (`01-content-addressing.md`), Kythe, and Glean — the substrate-practice space is systematically unpublished.
- **Lepiter** (GT's knowledge-base / multi-language notebook layer). Announcement: Gîrba, "Introducing Lepiter," [lepiter.io](https://lepiter.io/feenk/introducing-lepiter--knowledge-management--e2p6apqsz5npkdmxhfaqzqp5s/), 2021. `[not peer-reviewed — blog; no publication exists]` Citable only via the EuroPLoP 2024 name-check.
- **The GT "book."** No traditionally published book titled *Moldable Development with Glamorous Toolkit* exists — that title is a talk (YOW! 2023, GOTO 2024). What exists: the in-image live book at [book.gtoolkit.com](https://book.gtoolkit.com/) `[not peer-reviewed — artifact]`, and **Gîrba & Wardley, *Rewilding Software Engineering*** — a moldable-development book written in the open (Medium/feenk series, Feb 2025–, CC BY-NC-SA; index at [moldabledevelopment.com](https://moldabledevelopment.com/)) `[not peer-reviewed — book-in-progress]`.
- **Pharo** (the Smalltalk GT is built on). Standard citation is the book: **Black, Ducasse, Nierstrasz, Pollet, with Cassou & Denker — *Pharo by Example*,** Square Bracket Associates, 2009, ISBN 978-3-9523341-4-0. `[not peer-reviewed — book]` **No canonical peer-reviewed Pharo system paper exists.** Peer-reviewed anchors if needed: **Polito, Ducasse, Fabresse, Bouraqadi, van Ryseghem — "Bootstrapping Reflective Systems: The Case of Pharo,"** *Science of Computer Programming* 96:141–155, 2014, DOI [10.1016/j.scico.2013.10.008](https://doi.org/10.1016/j.scico.2013.10.008) `[verified]`; **Thomas, Ducasse, Tesone, Polito — "Pharo: A Reflective Language,"** *Journal of Computer Languages* 80 (2024), 101274, DOI [10.1016/j.cola.2024.101274](https://doi.org/10.1016/j.cola.2024.101274) `[verified]`.
- **Third-party uptake of "moldable" as a named approach** — evidence the term travels beyond one group: **Kavalar, Markovics, Rusher — "Clerk: Moldable Live Programming for Clojure,"** ‹Programming› 2023 Companion (PX/23), pp. 22–31, DOI [10.1145/3594671.3594682](https://doi.org/10.1145/3594671.3594682) `[verified]`; **Luna Cárdenas — "Grafoscopio,"** JOSS 2(18):251, 2017, DOI [10.21105/joss.00251](https://doi.org/10.21105/joss.00251) `[verified]`; **Valenzuela-Toledo, Bergel, Kehrer, Nierstrasz — "EGAD: A Moldable Tool for GitHub Action Analysis,"** MSR 2023, pp. 260–264, DOI [10.1109/MSR59073.2023.00044](https://doi.org/10.1109/MSR59073.2023.00044) `[verified]`; **Patkar — "Moldable Requirements,"** BENEVOL 2020, CEUR Vol-2912 `[verified — secondary]`.

## Tailorable systems and end-user programming — the lineage

- **Richard M. Stallman (1981) — "EMACS: The Extensible, Customizable Self-Documenting Display Editor."** *Proc. ACM SIGPLAN SIGOA Symposium on Text Manipulation*, pp. 147–156. DOI [10.1145/800209.806466](https://doi.org/10.1145/800209.806466). `[verified]` Extensibility via an interpreted extension language as the *organizing architectural principle* of a tool. **Three ACM DOIs exist** (proceedings + two reprint venues); use the proceedings one.
- **MacLean, Carter, Lövstrand, Moran (CHI 1990) — "User-Tailorable Systems: Pressing the Issues with Buttons."** pp. 175–182. DOI [10.1145/97243.97271](https://doi.org/10.1145/97243.97271). `[verified]` The "gentle slope" and the "tailoring culture": tailorability needs a spectrum from use to modification, sustained by a community sharing artifacts. The same use↔programming spectrum Edwards' substrate definition asserts (`09-scid.md`) — from HCI, thirty-five years earlier.
- **Bonnie A. Nardi (1993) — *A Small Matter of Programming: Perspectives on End User Computing.*** MIT Press. ISBN 978-0-262-14053-9, no DOI. `[not peer-reviewed — book]` End users do program when given task-specific formal languages (spreadsheets, CAD); the barrier is general-purpose languages remote from the task.
- **Anders Mørch (1997) — "Three Levels of End-User Tailoring: Customization, Integration, and Extension."** In Kyng & Mathiassen (eds.), *Computers and Design in Context*, MIT Press, pp. 51–76. No DOI; carried on IEEE Xplore as [document 6283297](https://ieeexplore.ieee.org/document/6283297). `[verified — secondary]` The standard depth taxonomy. **Semantic Scholar misattributes this chapter to the book's editors** — the author is Mørch.
- **Fischer & Giaccardi (2006) — "Meta-Design: A Framework for the Future of End-User Development."** In Lieberman, Paternò, Wulf (eds.), *End User Development*, Springer HCIS vol. 9, pp. 427–457. DOI [10.1007/1-4020-5386-X_19](https://doi.org/10.1007/1-4020-5386-X_19). `[verified]` Designers design the design space; systems as seeds evolved by owners of problems (the SER model). The standard single citation for meta-design.
- **Ko, Abraham, Beckwith, Blackwell, Burnett, Erwig, Scaffidi, Lawrance, Lieberman, Myers, Rosson, Rothermel, Shaw, Wiedenbeck (ACM Computing Surveys 2011) — "The State of the Art in End-User Software Engineering."** 43(3), art. 21. DOI [10.1145/1922649.1922658](https://doi.org/10.1145/1922649.1922658). `[verified]` The survey (14 authors). First author publishes as **Amy J. Ko** (originally printed as Andrew) — cite accordingly.
- **des Rivières & Wiegand (IBM Systems Journal 2004) — "Eclipse: A Platform for Integrating Development Tools."** 43(2):371–383. DOI [10.1147/sj.432.0371](https://doi.org/10.1147/sj.432.0371). `[verified — industry journal, editorially reviewed]` The citable anchor for plugin/extension-point IDE architecture — the mainstream compromise position between EMACS-style total malleability and closed tools.

## Malleable software — the current wave

- **Klokmose, Eagan, Baader, Mackay, Beaudouin-Lafon (UIST 2015) — "Webstrates: Shareable Dynamic Media."** pp. 280–290. Best Paper. DOI [10.1145/2807442.2807446](https://doi.org/10.1145/2807442.2807446). `[verified]` A persisted, synchronized DOM as a malleable substrate where the document/application distinction dissolves — the closest thing in HCI to a substrate claim, with *state* rather than code as the store.
- **Tchernavskij, Klokmose, Beaudouin-Lafon (‹Programming› '17 Companion, Salon des Refusés) — "What Can Software Learn From Hypermedia?"** art. 29. DOI [10.1145/3079368.3079408](https://doi.org/10.1145/3079368.3079408). `[verified]` The early framing of "malleable" as a software property. **Commonly miscited as two-author 2019 — it is three-author 2017.** The 2019 artifact is **Tchernavskij's thesis, *Designing and Programming Malleable Software***, Université Paris-Saclay, NNT [2019SACLS499](https://theses.fr/en/2019SACLS499) `[not peer-reviewed — thesis]`.
- **Borowski, Murray, Bagge, Kristensen, Satyanarayan, Klokmose (CHI 2022) — "Varv: Reprogrammable Interactive Software as a Declarative Data Structure."** 492:1–20. DOI [10.1145/3491102.3502064](https://doi.org/10.1145/3491102.3502064). `[verified]` Program behavior as declarative, additively-extensible *data* — the Webstrates lineage arriving at "the program is a store," from the UI side.
- **Grønbæk, Borowski, Hoggan, Mackay, Beaudouin-Lafon, Klokmose (UIST 2023) — "Mirrorverse: Live Tailoring of Video Conferencing Interfaces."** 14:1–14. DOI [10.1145/3586183.3606767](https://doi.org/10.1145/3586183.3606767). `[verified]` Live in-use tailoring demonstrated on a real application class.
- **Min, Chen, Cao, Xia (CHI 2025) — "Malleable Overview-Detail Interfaces."** 688:1–25. DOI [10.1145/3706598.3714164](https://doi.org/10.1145/3706598.3714164). `[verified]` And the framework follow-on: **Min & Xia (UIST 2025) — "Meridian: A Design Framework for Malleable Overview-Detail Interfaces,"** 200:1–14, DOI [10.1145/3746059.3747654](https://doi.org/10.1145/3746059.3747654) `[verified]`. "Malleable" as a headline term at CHI/UIST — the word has escaped the manifesto stage. Directly relevant pattern for arbor's three-pane UI: overview-detail is exactly the browser/detail split every prototype since p7 has shipped.
- **Litt & Jackson (‹Programming› '20 Companion, Convivial Computing Salon) — "Wildcard: Spreadsheet-Driven Customization of Web Applications."** DOI [10.1145/3397537.3397541](https://doi.org/10.1145/3397537.3397541). `[verified]` End-user customization of third-party apps via a synchronized spreadsheet view — a moldable-view move made by an outsider to the app.
- **Litt, Horowitz, van Hardenberg, Matthews (Ink & Switch, June 2025) — "Malleable Software: Restoring User Agency in a World of Locked-Down Apps."** [inkandswitch.com/essay/malleable-software](https://www.inkandswitch.com/essay/malleable-software/). `[not peer-reviewed — lab essay]` The manifesto for the current wave: gentle slope, composable tools over monolithic apps, communal tool-building. Ink & Switch's third appearance in this index (Cambria in `06-multi-language.md`, Peritext in `05-naming-versioning.md`).
- **Basman, Lewis, Clark (Onward! 2018) — "The Open Authorial Principle: Supporting Networks of Authors in Creating Externalisable Designs."** pp. 29–43. DOI [10.1145/3276954.3276963](https://doi.org/10.1145/3276954.3276963). `[verified]` What language/system properties let networks of authors of differing skill layer modifications on each other's artifacts without negotiated interfaces — the nearest thing to a published *requirements statement* for a commons of authors (`07-commons.md`).

## Where it plugs in

- `../design/06-architecture.md` layer 4 — first literature coverage of the interface layer. Moldable development is the named methodology a future interface prototype should consume rather than reinvent; the EuroPLoP 2024 pattern catalog is the concrete checklist.
- `../design/02-definitions-and-derived-data.md` — a moldable view over the store is a derived aspect; the eval-stability-for-tooling observation in §"Why this theme" is the candidate claim, recorded here rather than in `../design/decisions.md` because no prototype has exercised it.
- `09-scid.md` §"The current programme: substrates" — GT satisfies Edwards' substrate definition (persistent code & data store, direct-manipulation UI) and is unpublished, extending the artifact-without-a-paper pattern recorded there and in `01-content-addressing.md` (Unison).
- `07-commons.md` — the tailoring-culture line (Buttons) and the Open Authorial Principle are the social-argument citations for the commons vision; the malleable wave is that argument's current form.
- `02-structure-editors.md` — Barista and Deuce (already there) are tailorable-*editor* work; this file supplies the general tailorability lineage around them.
- `docs/prototypes/p7-web-interface/00-scope.md` and successors — the three-pane UI is an overview-detail interface; Min et al. name the malleability axes it lacks.

## Gaps and negative findings

- **Glamorous Toolkit has no system paper.** `[no publication exists]` for GT-as-system; the methodology papers carry it. Same pattern as Unison, Kythe, Glean.
- **Lepiter has no publication.** Blog announcement only; citable via the EuroPLoP 2024 name-check.
- **No published critique or independent empirical evaluation of moldable development exists** (2014–2026). Closest are adopter experience reports (Clerk, Grafoscopio, EGAD). The methodology's costs — view proliferation, maintenance of custom tools, the mutable-image invalidation problem — are undiscussed in print.
- **"Humane assessment" (Gîrba) has no publication** — method website, talks, and a card deck only.
- **No canonical Pharo system paper**; the book is the standard citation.
- **No DOI exists** for Nardi 1993, the Mørch chapter, the Tchernavskij thesis, or the Ink & Switch essay.
- Corrections carried to `00-index.md` hygiene candidates: Moldable Development Patterns is **EuroPLoP** 2024; the Moldable Inspector has **four** authors (Syrel third); the Moldable Debugger journal version **adds Denker**; the hypermedia paper is **2017, three-author**; Mørch is misattributed on Semantic Scholar; **Amy** J. Ko; Stallman 1981 has three DOIs.
