# Content Addressing and Merkle Structures

**Status:** Index. Sourced 2026-08-03. Annotations are observations, not substrate policy; see `00-index.md` §"How to read this".

## Why this theme

Content addressing is arbor's foundation. Prior art here is the densest and best engineered of any theme, and at arbor's granularity the least formalized. Every system below has the two-layer split arbor calls Store and Attachment: an immutable content-addressed layer with a mutable naming layer above it. Nix has store paths and profiles; IPFS has CIDs and IPNS; Perkeep has blobs and signed claims; Software Heritage has SWHIDs and origins. arbor's contribution is the split's granularity (per definition, where others work per file or per package) and its canonicalization (α-equivalence, so `\x. x` and `\y. y` collide).

Maziarz et al. below is the one rigorous technical result for that canonicalization. The survey's most important negative finding also lives here: Unison, the system arbor is closest to, has no peer-reviewed publication.

## Why content-address at all, rather than mint everything?

`../design/03-content-addressing.md` documents how arbor hashes but has no rationale section arguing why. If minting is available, one could issue a fresh key for every definition and keep a `key → data` map. That is simpler, never collides, and gives lineage for free. The question is what hashing buys that a UUID map cannot.

It buys four things, all consequences of one property: anyone can derive the identity from the thing itself, without asking permission.

- **Verification without trust.** RFC 062: *"Content-addressed paths on the other hand don't need a signature: if `/nix/store/123-foo` is content-addressed, then `123` is supposed to be a hash of the content of the path, and that can be easily checked."* A `key → data` map requires trusting whoever holds the map. Hashing makes the store untrusted: any mirror, peer or agent can serve a definition and the recipient can check it. RFC 062 draws the consequence: *"several users can share the same Nix store, but have each a different trust relation to it."* For arbor this is what makes a shared commons possible without a central authority, and what stops an agent misrepresenting what a definition contains.
- **Agreement without coordination.** Two parties who independently produce the same definition arrive at the same name without communicating. Under minting they get different names for the same thing and can never discover the match. This is the property arbor's agentic claim rests on, and it belongs to content addressing, not to immutability: an append-only UUID store is immutable and does not converge at all. "Immutability prevents collisions" really means convergence without coordination.
- **Cache keys that are theorems.** Same hash implies same content implies same derived result. That is eval-stability, and it costs nothing. Under minting, "these two keys denote equal content" is a separate fact somebody must establish and maintain. Nix pays that price: input-addressing means a cosmetic change to a low-level dependency renames every downstream path even when outputs are byte-identical, and RFC 062's build cutoffs exist to recover what content addressing gives for free. Its dedup mechanism is stated the same way: *"if `drv` and `drv'` only differ because one depends on `dep` and the other on `dep'`, but `dep` and `dep'` are content-addressed and have the same output hash, then `resolved(drv)` and `resolved(drv')` will be equal."*
- **Immutability by arithmetic.** Content cannot be altered without altering the name. A UUID map can achieve the same through append-only discipline, but discipline is a policy that can be violated, misconfigured or raced. Hashing makes it a property of the numbers.

Deduplication is the most often cited benefit and the least important one here. It is decisive at Software Heritage's scale (16B+ files) and near-irrelevant at arbor's. Convergence and cache keys as theorems carry the design.

### What content addressing cannot do, and why every system layers

Every benefit above concerns sameness; none concerns identity through time. Minting supplies the latter for free: stable identity across edits (arbor's mint thread), deliberate distinctness of coincidentally equal things (arbor's mint), the ability to say "this moved" (Grove's objection that a hash cannot express a move), and privacy (a hash is a confirmation oracle: anyone can test whether you hold specific content).

Minting everything would lose verification, convergence and free cache keys. Hashing everything would lose lineage, deliberate distinctness and movement. In practice no system chooses; every deployed system in this file runs both layers:

- Git — content-addressed objects, mutable refs.
- Nix — hashed store paths, mutable profiles and generations.
- IPFS — CIDs, IPNS.
- Perkeep — content-addressed blobs, permanodes, signed claims.
- Software Heritage — intrinsic SWHIDs, extrinsic origins and snapshots.
- arbor — hashes, the namespace, and mints.

Di Cosmo, Gruenpeter & Zacchiroli's **intrinsic** identifiers, as opposed to issued ones, draw the same distinction (their own paired vocabulary is DIO/IDO; see §"What the Software Heritage identifier papers actually argue"). Issued, non-derivable identity does not compete with content addressing. It is the layer every system ends up building on top of it, because the four properties above are bought by giving up identity through time. arbor is unusual in placement: it puts extrinsic identity inside the intrinsic layer, in the same node as semantic content. Perkeep keeps identity in separate content-free blobs, and Git keeps refs outside the object store entirely. That divergence is tracked at `../design/open-questions.md:84`.

### The hard limit: self-reference

Nix documents the deepest constraint. Content addressing cannot name a thing that refers to itself, because the name depends on the content, which depends on the name. Nix meets this as self-referential store paths. It works around them by building at a placeholder path and rewriting hashes afterward, and admits the fix is partial: hash rewriting *"is only a heuristic and there is no way to truly ensure that we don't leak a self-reference."*

arbor hits the same wall, recorded at `../design/open-questions.md` §"Content addressing" as "Mutual recursion canonicalization." Unlike Nix, arbor has structured syntax in place of opaque bytes, which admits more than one way out. Unison's is to make the recursive group a single addressable unit, with intra-group references by index. The alternative is to close the cycle with a binder in the object language (a fixpoint over a product, with the members as projections), which leaves the store's key type alone. It does not remove the canonical-ordering ambiguity that Unison's approach only partially solves; it changes what the ambiguity costs, from a rejected ingest to an arbitrary but behaviour-preserving choice. This is worked through in `../design/03-content-addressing.md` §"Mutual recursion: three ways to close the cycle". *(Corrected 2026-08-07: this entry previously called Unison's approach "the standard answer," which foreclosed a choice arbor has not made.)* Both routes convert a self-referential object into a closed one, which Nix cannot do because its outputs are opaque bytes.

A citation this theme lacks: canonically ordering a mutually recursive group is **graph canonization**, assigning canonical indices to the vertices of a labelled digraph. The erase-then-sort technique both approaches use is one round of the colour-refinement idea underlying Weisfeiler–Leman, with the same known incompleteness. That is why Unison's failure mode is intrinsic and not an implementation gap. The claim is currently asserted from reasoning in `../design/03-content-addressing.md` with no source; source the canonical-labelling literature before leaning on it. `[gap — not yet searched]`

RFC 062 also names the causal constraint behind Nix's default: *"we can't know the output paths of a derivation before building it."* Content cannot address something that does not exist yet, so input-addressing is a workaround for needing a name before the content. arbor mostly escapes this because its definitions are source, not build outputs; it names things that already exist. The constraint resurfaces only when naming what has not been written yet, and p8/p9 answer it differently from Nix. A bare `Hole` has a constant hash, so all holes are the same thing. Nix needed placeholders to be unique; arbor makes them identical.

### What the Software Heritage identifier papers actually argue

Read in full 2026-08-03: the 2020 CiSE article. The 2018 paper is still unread. It supplies vocabulary arbor can adopt wholesale.

**Terminology.** *Intrinsic* is their term: *"the key insight is that to get all the nice properties above one must build identifiers **from the object itself**, using for example a hashing function, and this is why we call this kind of identifiers **intrinsic**."* Their paired distinction is not intrinsic/extrinsic, and the word "extrinsic" does not appear in the 2020 paper. Their pair is **DIO vs. IDO**, from re-reading the DOI acronym via Paskin: *"The term 'Digital Object Identifier' is construed as 'digital identifier of object', rather than 'identifier of a digital object'."*

- **DIOs — Digital Identifiers *of* Objects.** DOI, Handle, ARK, PURL, URN. They can name any kind of object, "including people, or organizations, that have no canonical digital representation," and therefore "inherit all the epistemic issues of the traditional naming systems: the need of a central authority, the complexity related to handling different manifestations of the same conceptual object."
- **IDOs — Identifiers *for* Digital Objects.** Restricted to digital objects, "which means giving up the ability to attach identifier to any kind of objects (like persons, ideas or institutions), but in exchange all the properties that are difficult or impossible to satisfy in traditional systems of identifiers become feasible."

The frame trades scope for properties: a narrowing that buys guarantees. arbor is an IDO system, and it gets its guarantees because it names nothing that is not a stored definition. Where this directory uses "extrinsic", it is a convenient complement, not their word; it may appear in the unread 2018 paper. `[do not attribute "extrinsic" to them without checking]`

**The six mechanisms**, the most directly reusable part of the paper. A system of identifiers is a set of labels plus mechanisms performing some of: **Generation** (create a new label), **Assignment** (associate a label to an object), **Verification** (given a label and an object, verify that they correspond), **Retrieval** (given a label, get a copy of the object), **Reverse lookup** (given an object, find the label assigned to it), **Description** (given a label, get metadata describing the object). Most systems "conflate all these conceptually distinct mechanisms into a single logical component usually called *resolver*."

Three observations for arbor. Content addressing fuses Generation and Assignment, since the label is derived. Minting separates them, which makes a mint a different kind of object from a hash and not a variant of one. Description is the aspect store. And the paper notes that none of Handle, DOI, ARK or PURL supports reverse lookup (Table I), whereas content addressing makes it free: you compute the hash. Dedup-on-ingest, "have I seen this definition before," and `Store.callers_of` are all reverse lookup, a benefit arbor's docs never name.

**Seven properties**: Uniqueness, Non-ambiguity, **Integrity**, Persistence, **No middleman**, **Abstraction** (preferred to "opacity", by analogy to Abstract Data Types), Gratis. Integrity is arbor's headline theorem in their words.

- **Integrity:** *"one expects the object denoted by an identifier not to be **silently changed** later on. An identifier ensures integrity if a user can verify that the object retrieved at any point in time is exactly the one that was associated to it at the beginning."* This is no-silent-breakage stated as a property of an identifier, down to the word "silently". Their validation adds: *"using a cryptographic hash as identifier ensures that modifications to the denoted object, however minimal, would yield a different identifier with an extremely high probability."*
- **No middleman:** *"one should not rely on intermediaries for assigning identifiers in the beginning or using them later on. The name of this property is borrowed from security and cryptography."* Validated as *"the link between an object to its identifier does not depend on the resolution of an online service. These identifiers can be used and verified outside the system that creates and maintains them."*
- **Gratis** carries the convergence claim: *"By construction the obtained identifiers will be the same everywhere, allowing cross-checking."*

Figure 3 stages the trust argument in three steps. A DOI resolver without checksums requires trusting the whole toolchain. With checksums in metadata the archive is no longer trusted, but DOI intermediaries still are. SWHIDs *"minimize the trusted parties and channels: only a reliable checksum verifier is needed."*

**The precondition**, stated as a limitation, illuminates arbor most: *"This approach only works well if the digital object has a **canonical representation**, on which the hashing function can be applied: it will not be very useful for identifying documents like research articles, that can be represented in various formats, but is perfectly suited for software artifacts."*

They treat canonical representation as something an object has or lacks. arbor manufactures it. α-equivalence canonicalization constructs a canonical representation where the surface syntax has none, which extends the reach of intrinsic identifiers. That is a sharper account of what canonicalization is for than `../design/03-content-addressing.md`'s "structural sharing is the point."

**They raise the lineage problem and leave it open:** *"An object may be used to create a new object that is a modification of the first one, and one may want to keep track of the fact that the second one is derived from the first one. Some systems of identifiers allow to encode this versioning information **in the object label**. Similarly, an object may be composed of several other objects, and some systems of identifiers may want to encode in the object label the relation of containment."* Encoding derivation in the label is what a mint does, so §"Coincidental convergence" below is a recognized gap in identifier-system design, not an arbor peculiarity. They describe contextual information as existing for this purpose: *"not strictly needed for reproducibility, but it is convenient to store extra information, like the location from where the archived source code has been obtained, **to allow tracking future evolution** of referenced software artifacts."*

**Contextual information.** Table II's EBNF admits only `origin` and `lines`: `<identifier_with_context> ::= <identifier> [<lines_ctxt>] [<origin_ctxt>]`. The fuller qualifier set (`visit`, `anchor`, `path`) is the current spec, not the 2020 paper; do not attribute it to the paper. Either way the structure is an intrinsic core plus a context channel, one carrying what the object is and the other where it was found and how it evolves. Git objects/refs and arbor's Store/Attachment split have the same layering, here compressed into one string.

**Registry death.** Their Parmap showcase: a 2012 article referenced its code at `gitorious.org/parmap`. Gitorious closed in June 2015 and the URL broke; only the archived copy, addressable intrinsically, survived. The paper's conclusion states the separate-concerns thesis: *"while citations are essential for giving credit, references are sufficient for reproducibility."*

**Worth pulling from their reference list:** Arnab & Hutchison, "Verifiable digital object identity system," DRM '06 (the verification-gap citation); Paskin, "Digital object identifier (DOI) system," *Encyclopedia of Library and Information Sciences*, 2010; Arms, "Uniform resource names: Handles, PURLs and digital object identifiers," *CACM* 44(5), 2001. `[verified as entries in this paper's bibliography; not independently checked]`

## Hashing modulo an equivalence — the core primitive

- **Krzysztof Maziarz, Tom Ellis, Alan Lawrence, Andrew Fitzgibbon, Simon Peyton Jones (PLDI 2021) — "Hashing Modulo Alpha-Equivalence."** DOI [10.1145/3453483.3454088](https://doi.org/10.1145/3453483.3454088); arXiv:[2105.02856](https://arxiv.org/abs/2105.02856). `[verified]` **[Priority read.]** The one rigorous result for the primitive arbor depends on: hashing binding structure so α-equivalent terms collide, in O(n log²n) instead of O(n²), via a weak commutative hash combiner used at one point, with a proved collision bound. This is the citation for arbor's α-equivalence by canonicalization. De Bruijn gives the representation, not the hashing result, and Unison has no publication.
- **Jean-Christophe Filliâtre & Sylvain Conchon (ML 2006) — "Type-Safe Modular Hash-Consing."** DOI [10.1145/1159876.1159880](https://doi.org/10.1145/1159876.1159880). `[verified]` Maximal sharing behind an abstract type, parameterized by an arbitrary equivalence. The parameterization is the direct precedent for canonicalization: hash-consing modulo α-equivalence is hash-consing modulo a user-supplied relation.
- **M.G.J. van den Brand, H.A. de Jong, P. Klint, P.A. Olivier (2000) — "Efficient Annotated Terms."** *Software: Practice and Experience* 30(3):259–291. `[verified]` ATerms: maximal subterm sharing, automatic GC, and a compact binary exchange format so shared terms move between processes. The nearest ancestor of `CLAUDE.md`'s "typed values at substrate APIs, serialization internal to the layer that needs it."

### What Maziarz et al. §2.4 rules out, and why it does not touch p4

Read 2026-09-16, §§2.3–2.5 only (¶8–11 of the arXiv text), via the local Zotero fulltext index.

§2.4 reads at first like a refutation of arbor's headline canonicalization claim. It asks whether de Bruijn indexing solves α-equivalence hashing and answers *"Sadly, no: using de Bruijn indexing remains vulnerable to both false positives and false negatives."* The two counterexamples:

- **False negative.** In `\t. foo (\x.x+t) (\y.\x.x+t)` the two `(\x.x+t)` subterms are α-equivalent, but de Bruijn renders them `(\.%0+%1)` and `(\.\.%0+%2)`: the free `t` gets a different index under each.
- **False positive.** In `\t. foo (\x.t*(x+1)) (\y.\x.y*(x+1))` the two subterms are not equivalent, but both render `(\.%1*(%0+1))`. And *"unlike with simple syntactic equivalence, these false positives cannot be eliminated by giving every binder a unique name — with de Bruijn there are no binders!"*

This does not contradict p4. Both counterexamples turn on a variable bound by an enclosing lambda, and they address the paper's problem, not arbor's. The paper's goal (§3) is to *"identify all equivalence classes of subexpressions of e"*: a subterm's hash must be stable under its context, because the application is CSE inside a compiler. arbor hashes whole definitions, and those are closed: bound variables are de Bruijn and free names resolve to a `Ref(hash)`. So de Bruijn canonicalization is sound for α-equivalence, and `\x. x` and `\y. y` do collide. The claim in `../design/03-content-addressing.md` stands, but its scope (closed terms) should be stated alongside it; the design docs currently leave it implicit.

Closedness is a property of the resolver path, not an enforced invariant. `Resolver.resolve` returns `Unbound_name` for a free name (`prototypes/p4-lambda-calculus/src/resolver.re:54`), so nothing open reaches the Store in practice. But `Ast.t` admits open terms, and `Ast.is_closed` is used only by the pretty-printer and one test, never by `Store.ingest`. If closedness is what makes the α-equivalence claim true, `Store.ingest` is the obvious place to check it, alongside "no cross-language references."

§2.4 does bite on the subterm-hashing idea. Priority read 9 in `00-index.md` proposes co-contextual type rules so that "a de Bruijn *subterm's* hash" could key a type-check aspect below the definition root. §2.4 rules out that move: an open subterm's de Bruijn hash is neither sound nor complete for α-equivalence, so such a cache would miss hits and, worse, collide across distinct terms. Anyone picking up item 9 should read §2.4 first.

The second cost is asymptotic and applies to arbor as built. §2.5 notes that under de Bruijn (and locally nameless, *"used in Epigram and the LEAN theorem prover"*) the hash of `(\x.e)` cannot be derived from the hash of `e`: *"as we pass each lambda, we must re-hash the entire body."* Every arbor prototype re-hashes whole definitions on every keystroke, so the cost is latent at prototype scale. It is the reason the paper's algorithm exists, and p21's "typing is saving" makes the inner loop where it would first be felt.

## Minting — identity that is not a function of content

`../design/10-minted-identity.md` carries no citations; this section anchors it. The question is what else in the content-addressing world defeats structural collapse on purpose by putting a fresh mark inside the hashed bytes. The closest match is not in IPFS.

- **Perkeep permanodes.** [perkeep.org/doc/schema/permanode](https://perkeep.org/doc/schema/permanode). `[verified by fetch 2026-08-03; not peer-reviewed — schema documentation]` **[Priority read — short, and it is arbor's mint already built.]** A permanode is a cryptographically signed random value. The schema field is literally `"random"`, documented as *"Any random string, to force the digest of this node to be unique."* It serves as a stable identity anchor for a mutable thing inside an immutable content-addressed store. Mutation happens through separate signed `claim` blobs referencing the permanode, and current state is a replay of claims in chronological order. That is p11's mint thread plus append-only binding history, shipped.

  Two differences bear on open questions. (1) A permanode carries no content; it is a pure identity token, and content lives in the claims pointing at it. arbor's mint is a field inside a definition that also carries content. Perkeep factors identity and content into separate blobs where arbor fuses them. `../design/open-questions.md:84` poses this choice ("first-class field with a sentinel, a separate constructor, or an aspect"), and Perkeep is the separate-node answer with production history behind it. (2) The permanode is signed, which is how it resists forgery. That is the deferred "mint-as-keypair" path in `../design/open-questions.md:100`, already in real use.
- **Unison's `unique` / `structural` keywords.** [unison-lang.org/docs/language-reference/unique-types](https://www.unison-lang.org/docs/language-reference/unique-types/). `[verified by fetch 2026-08-03; no publication exists]` **[Priority read — one page, and it answers two of arbor's open questions.]** Already credited at `../design/open-questions.md:80` as "Unison-style `unique` per definition." Confirmed mechanism: "When compiling these declarations, Unison will generate a universally unique identifier for the type and use that identifier when generating the hash for the type. As a result, the type gets a hash that is universally unique." Structural declarations are written `structural type Optional a = Some a | None`, and Unison shows the structural hash directly (`#5isltsdct9fhcrvu`), so `Optional` and `Maybe` are one type.

  **Unison mints types by default, confirmed in source 2026-08-07.** The 2026-08-03 sweep inferred this from rendered output: the page renders the minted declaration as a bare `type Suit` while every structural example keeps `structural`, as expected if the pretty-printer drops `unique`. Both halves of the inference now have primary evidence. A declaration parsed with no modifier calls `resolveUniqueTypeGuid` (`parser-typechecker/src/Unison/Syntax/DeclParser.hs:230`), the GUID enters the hash as `[Tag 1, Text guid]` (`unison-hashing-v2/src/Unison/Hashing/V2/DataDeclaration.hs:130-132`), and the printer drops the keyword (`DeclPrinter.hs:304`). `[source-verified @ db60ce2]` This closes the gap recorded in §"Gaps and negative findings" below.

  Unison's own design doc has it backwards: `docs/data-types.markdown` says structural "is the current default" and proposes `nominal type` as hypothetical syntax. The intent inverted between doc and implementation and the doc was never updated. A system's prose is evidence about its designers, not about its behaviour.

  Three consequences for arbor. (1) The closest comparable system ran p10's mint-everything experiment for types and kept it as the default. (2) Unison mints types but not terms. That is a third answer to `../design/open-questions.md:80`, absent from arbor's own framing: per sort, where arbor lists per definition and per language. arbor has already converged there (p16/p17 mint only labels, p12 mints `Opaque` types, terms stay structural), so Unison and arbor's current line agree, and p10's mint-everything is the outlier in both. (3) From the source read: minting has recurring upkeep, and Unison's is ad hoc. With no explicit *edit-of-X* gesture, it recovers a type's GUID by name when re-saving, choosing *"an arbitrary one"* where the name is conflicted (`UniqueTypeGuidLookup.hs:19-20`), and needs a `namespace_unique_type_guid` side table to keep branches from minting independently. This is evidence both for p11's explicit-gesture design and against its completeness; see `../systems/unison/04-caching-update-merge.md` §"Minting".
- **"Minting" is the persistent-identifier community's literal verb.** [arks.org](https://arks.org/) has sections titled "Minting ARK name strings" and "Best practices for minting ARK name strings". ARKs are issued by a Name Assigning Authority (NAAN), and DOIs likewise via DataCite and Crossref. `[verified by fetch 2026-08-03; not peer-reviewed — community documentation]`

  This gives a sharper characterization than `10-minted-identity.md` has. Di Cosmo et al. call an identifier built from the object itself **intrinsic** (§"What the Software Heritage identifier papers actually argue" above). An issued identifier is the complement: assigned by an authority, checkable only by asking it. A mint is then an issued identifier embedded in an intrinsic one, the one part of the hash that cannot be recomputed from the definition, only read back out. That explains what it does and why it breaks "the hash is a pure function of content." `10`'s current framing, "opt-in axis of identity, orthogonal to content addressing," is true but weaker. *Intrinsic* is Di Cosmo et al.'s term; *extrinsic* is not (their pair is DIO/IDO), so use it as a complement, not a quotation.
- **Nix's input-addressing: a loose analogy and a real cost argument.** Nix's default store path hashes the build inputs, not the output, so two derivations with byte-identical output land at different paths. That is identity which is not a function of content. The analogy to minting is weak: input-addressing is deterministic (a function of inputs), and a mint is fresh (a nonce). The consequence is shared, but mechanism and intent differ; do not present them as the same idea.

  The cost transfers. When identity is not a function of content, the system cannot notice that two things are the same, so it loses early cutoff and pays in redundant downstream work. Nix's mass-rebuild problem is that cost at scale, and content-addressed derivations (RFC 062, see `04-incrementality.md`) exist to recover it. In arbor, a minted definition cannot share derived aspects with its structural twin, so it is type-checked and evaluated twice. The cost is bounded in arbor as it is not in Nix, because arbor's minting is scoped (labels, abstract types) where input-addressing is pervasive and incidental. It is still why mint-everything (p10) is not free.

  Chronology: Dolstra's 2006 thesis describes the content-addressed intensional store as the more desirable design. The roughly fifteen-year gap is time to implementation, not an effort to discover or remove anything. Nothing was removed: input-addressing remains Nix's default, with CA derivations experimental and opt-in.
- **Git's accidental mint.** A commit object includes author and committer timestamps, so otherwise-identical commits differ. This is de facto minting, never designed as identity machinery, and a known footgun when timestamps do coincide and two commits collapse. A caution against minting by incidental metadata in place of an explicit mark.
- **The mark is a nonce, and commitment schemes are the right frame.** A mint mark is a number used once, mixed into a hash preimage to force distinct digests: the same construction as the salt in a salted hash commitment. Two properties follow. **Binding is inherited free:** the digest still commits to the content, so minting changes only which definitions fall in the same equivalence class, never the no-dangle or immutability guarantees. **Hiding is not wanted:** cryptography adds the nonce so an observer cannot recover a low-entropy value, which forces the salt to be secret and high-entropy. arbor adds it only so equal definitions do not collapse, which requires nothing but uniqueness. The mark can therefore be public, and "mint-as-keypair" (`../design/open-questions.md:100`) is a real escalation because it introduces a secrecy requirement that distinctness does not carry. This also answers `:83` ("how marks are minted"): used once is the whole requirement. The standard answers are a counter (certainly unique, needs coordinated state) or randomness (unique with overwhelming probability, needs no coordination). Random is the usual pick in distributed or multi-agent settings, for the reason arbor cares about. `[framing; the specific literature on hiding commitments in Merkle structures was not chased this session]`

### Coincidental convergence — the problem minting actually solves

The sharpest case for a mint is a lineage hazard, more than Meters vs. Feet. Two distinct concepts `A` and `B` are each edited and arrive at structurally identical content `C`. Under pure content addressing the two histories collapse at `C`: there is one `C`, and the fact that one arrived from `A` and the other from `B` is lost. After further edits `C ⇒ A'` and `C ⇒ B'`, neither is attributable. A fresh mark at each authoring prevents the collapse.

The problem is well known, though rarely in the content-addressing literature. Four framings, roughly in order of closeness:

- **The ABA problem** (concurrent programming). A location goes A → B → A; a compare-and-swap observes the original value and concludes nothing changed, when the world moved underneath it. The textbook fix is minting: attach a monotonic counter to the pointer (tagged pointers, double-width CAS) so the "same" value stays distinguishable. Coincidental equality defeats change detection, and a nonce restores it. arbor's collapse at `C` is a structural ABA. `[textbook material; no specific citation chased]`
- **Surrogate vs. natural keys** (database design). A natural key is derived from the data; a surrogate key is arbitrary. The standard argument for surrogates names arbor's two failure modes: distinct real entities coincidentally sharing attribute values, and attributes changing over time. Kimball's **Type 2 slowly-changing dimensions** split it as arbor does: a new surrogate key per version for per-version identity, plus a durable key grouping versions into one thread. That is hash-plus-mint in warehousing vocabulary, and the closest thing to a mature engineering consensus on the trade-off. `[well-established practice; primary sources not chased this session]`
- **CRDTs cannot content-address their elements, for the same reason.** In a sequence CRDT two concurrently inserted `"a"` characters must remain distinct, so every element carries a unique ID (RGA, Logoot, Treedoc, Automerge). Content-addressing characters would collapse concurrent equal insertions and destroy intent. Grove makes the same move at AST granularity with per-vertex and per-edge UIDs, so the system nearest arbor in Hazel's own line reached this conclusion from the concurrency side. See `05-naming-versioning.md` and `02-structure-editors.md`.
- **Git solves it without a nonce**, and this is the design alternative worth weighing. Git blobs and trees collapse on identical content. Commits do not, because a commit's hash includes its parents. So `A ⇒ C` and `B ⇒ C` produce two distinct commits sharing one tree: lineage preserved, content still deduplicated, no nonce anywhere.

The Git comparison matters for `../design/10-minted-identity.md`. Under minting, `C_a` and `C_b` are different definitions, so `C` is type-checked and evaluated twice: the early-cutoff cost from §"Why content-address at all" in concrete form. Under a predecessor-carrying edit node, one `C` is stored with one set of aspects and the threads still separate. For the lineage role, a parent pointer is strictly cheaper than a mint.

It covers only half the case, and the split matches p12's finding at `../design/10-minted-identity.md:58`. If marks are fresh per authoring, `A(m₁) ⇒ C(m₃)` and `B(m₂) ⇒ C(m₄)` already fail to collapse. Freshness prevents the collapse, and the thread is carried by the edit log or the namespace, not by the mark. So the scenario is satisfied by dies-with-hash plus an edit log. It argues for p12's position; marks-survive only adds grouping by mark without consulting the log. A mint is irreplaceable in the distinctness role (Meters vs. Feet), because there every reference must carry the distinction, and a parent pointer in a separate layer cannot: `Ref(hash-of-C)` would not know which concept it meant.

IPFS and IPLD have nothing native. Content addressing is collapse by content by definition, and neither has a first-class nonce or identity-token concept. IPNS is a mutable pointer keyed by a public key, which is the naming layer (arbor's Attachment), not a mint. Adding a random field to a DAG node to force a distinct CID is real folk practice, but it carries no semantics and has no name in the specs. `[weak negative — targeted fetches only; WebSearch budget was exhausted, so this is not an exhaustive IPLD sweep]`

## Gaps and negative findings

- **No peer-reviewed Unison publication.** See above; also relevant to `../design/open-questions.md` and the `formalism/` line's positioning. Still true after the 2026-08-07 source read, which supplies evidence, not a specification: none of Unison's design claims is stated as a property anywhere in the tree. The read strengthens the positioning, since the never-invalidated cache is implemented by omitting invalidation, a property nobody wrote down.
- **No academic treatment of Git's object model.** Use Bird et al. plus *Pro Git*; do not imply a paper exists.
- **No prior work found on canonicalized-AST hashing as a program-store primitive** beyond Maziarz et al., which treats it as an algorithm, not a storage model. This appears to be open ground, but it is a negative finding from a budget-limited search, not a proof of absence.
- **Content-defined chunking is a red herring for arbor.** Cite it only to explain why AST-shaped boundaries are preferable.
- **No first-class minting concept in IPFS or IPLD**, and the folk practice of a nonce in a DAG node has no name or semantics in the specs. Weak negative: targeted fetches, not a sweep.
- ~~**Unison's unadorned `type` default is undocumented.**~~ **Closed 2026-08-07** by the source read: `DeclParser.hs:230` shows a declaration with no modifier minting a GUID, so Unison is unique by default. This remains undocumented (the language-reference page never says it, and `docs/data-types.markdown` says the opposite) but is resolved. See §"Minting" above.
- **This theme has no slot for what Unison deleted.** Metadata links, `Patch`/`propagate` and the SQL name index were all removed between 2024 and 2025, each replaced by derivation or convention. No publication carries this evidence about content-addressed program stores, and it bears on the primary-store-vs-derived-index gap recorded in `09-scid.md`. Recorded in `../systems/unison/05-deletions.md`.
- **Salted/hiding commitments were not chased.** The mechanism is identical to minting and the motivation is not; a proper look would say whether anything transfers.
