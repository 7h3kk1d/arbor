## Associated data

- **Is the asserted/derived split load-bearing rather than descriptive?** *(New 2026-08-07, from the Unison source read.)* Unison built essentially this mechanism — extensible per-definition metadata, categories identified by convention rather than by type, values themselves content-addressed references, hashed into the namespace — and **deleted it in January 2024**. Tracing each of its motivating categories: API docs became a naming convention (`foo.doc`); is-this-a-test became a **type query** (a test is any term of type `[Test.Result]`); author, copyright holder, and license went **nowhere** and are now unattached definitions under `metadata.*`; creation date and subpath comments were never built. Meanwhile the categories keyed by **hash** and written by **the system** — the type index, the dependents index, the evaluation cache — all survived and grew. The discriminator is key shape, not assertedness: what died was keyed by (definition, *name*) and so duplicated the namespace without inheriting its aliasing, merge, history, or suffix resolution. arbor's own aspects are all the surviving kind (`Type_of`, `has-holes:v1`, `follow-clean:v1`, translation targets, the eval cache). Open: should `02-definitions-and-derived-data.md` *weight* the two halves rather than treating them symmetrically; is an author-asserted name-shaped fact better off as a definition with a name; and if so, what happens to the categories that then have nowhere to live — since Unison's answer was to drop them silently. Note also that one of the four forces (being *in* the namespace hash, so annotating becomes a structural change) does not apply to arbor, whose aspects sit outside Σ's hash by construction — worth stating in `02` rather than leaving as an accident of the model. Argued in full in `../systems/unison/09-side-structure.md`; the *why* there is inference from evidence, not a stated rationale.
- **Vocabulary for "aspect."** Chosen provisionally to avoid TAPL-kind collision. Alternatives if friction appears: *facet*, *annotation*, *attribute*, *channel*.
- **Conflict handling.** When an asserted entry and a derived entry disagree on the same logical property (annotation says `Int→Int`; inference says `Bool→Bool`), the substrate records both. What's the default surface behavior?
- **Where aspect descriptors live.** Per-language module, global registry, or both? Big practical consequence for the tech stack.
- **Cross-aspect dependencies.** Evaluation depends on types; translation may depend on elaboration. Formalize as an aspect-dependency graph, or handle ad hoc in each procedure?
- **History of asserted entries.** Names and descriptions change. Do we keep edit history, and at what granularity? Ties into eventual branching.
- **Graduating from tag+version to content-addressed procedures.** What concretely triggers that migration? Probably when we have a stable meta-language candidate and enough derived-entry cache volume to justify precise invalidation.

## Content addressing

Addressed in `03-content-addressing.md`:
- ~~Canonicalization.~~ Syntactic by default, α-equivalence at minimum, per-language declarations allowed; coarser (semantic) equivalences are per-language opt-ins left open.
- ~~Primitive / builtin identity.~~ Manually-versioned tags, same model as procedure identity.

Still open:
- **Mutual recursion canonicalization.** When a language introduces mutually recursive definitions, the substrate needs a way to close the cycle. **Three options as of 2026-08-07, none chosen** — (A) Unison's component: hash the group as one object, address members by index; changes `Σ`'s type to `Hash ⇀ Node⁺` and **refuses** when two members are structurally identical modulo intra-group references. (B1) A fixpoint over a **positional tuple**, members as projections: leaves `Σ` unchanged, needs no mints, reuses p17's `Pair`/`Fst`/`Snd`; the bundle's hash is invariant under group automorphisms, so the bad case costs only an arbitrary-but-behaviour-preserving choice of which projection is which — a coincidental non-collapse rather than a rejected ingest. (B2) The same over a **labeled record**: restores presentation-independence in that case, but by converting the canonicalization question into a *name-keyed mint-stability* question, not by dissolving it. The real fork is **a mint versus a rare loss of presentation-independence**. Worked through in `03-content-addressing.md` §"Mutual recursion: three ways to close the cycle", which also records that canonically ordering a recursive group is graph canonization, so no cleverer hash makes (A)'s failure go away. This entry previously named only (A). Not urgent.
- **Holes and incomplete programs.** If the substrate eventually hashes incomplete programs (Hazel-style editing), how do holes participate in the canonical form? Unique hole identities, subsumption-style matching, or something else?
- **Cross-version primitive aliasing.** If `int:add:v1` and `int:add:v2` differ only cosmetically, callers of v1 are orphaned. Any aliasing story, or just accepted cost?
- **Hashing types as well as terms.** Types are currently inline in term encodings; p6 hashes types only for procedure-id encoding, not as definitions. Promoting types to first-class content-addressed objects gives type aliasing for free via the namespace, and changes how `Type_of(...)`-shaped aspect values are stored. Sharpened in `03-content-addressing.md` under *Threads under exploration*.
- **Hash algorithm.** Not locked in; bootstrap accepts full rebuilds. Choice will come when we need one.

## Naming layer

- **Scope of names.** Per-user, per-"workspace," global? Unison uses namespaces; we'll want to punt on structure but should not paint ourselves into a corner.
- **Dependency-depth priority in suffix resolution.** *(New 2026-08-07, from the Unison source read.)* p9/p10/p17 resolve a bare suffix only when it is unambiguous, and report `Ambiguous` otherwise. Unison adds a rule arbor has no equivalent of: names nested more deeply beneath a `lib` segment **lose** ties, so `map` resolves unambiguously to `lib.base.List.map` even though `lib.something.lib.base.Set.map` also ends in `map` (`unison-core/src/Unison/Name.hs:597-599`). Without something like it, vendoring a dependency that itself vendors a dependency makes every common suffix ambiguous. Open: is depth-priority an editing-layer resolution policy or a substrate-level property of the namespace, and does it require the substrate to know that some segments (`lib`) are special? Sourced in `../systems/unison/03-namespace-and-history.md` §"Suffix resolution".
- **Names that denote things with no hash.** *(New 2026-08-07, from the Unison source read.)* Unison distinguishes `Reference` (a definition) from `Referent` (what a term-position name may denote: a term *or* a data/effect constructor). A constructor has no hash of its own — it is addressed as (declaring type's hash, ordinal) — so `Maybe.Just` is a legal name for something that is not a stored definition. arbor's namespace maps names to hashes, full stop. p16's label sort answers an adjacent question differently: a label *is* a first-class stored definition with its own hash. Open: when a language in the substrate gains datatypes with constructors, do constructors become definitions (arbor's label answer) or relative references (Unison's answer), and does `N`'s codomain have to widen? Sourced in `../systems/unison/03-namespace-and-history.md` §"Referent vs Reference".
- **Name → hash resolution timing.** Strictly at edit time, or also at some kind of "load" step for interfaces?
- **Unifying namespace and aspect-store lifecycles.** When branching arrives, does a shared "container" (or whatever name emerges) make sense, or do we keep them parallel? See the cross-reference sections in `02` and `04`.
- **Name structure: hierarchical paths.** Editing-layer convention, substrate-aware paths, or substrate-fixed format? Bound up with when namespace branching enters scope. Sharpened in `04-naming-layer.md` under *Threads under exploration*.
- **Name structure: tags.** Many-to-many name-shaped attachments. Tentative reading is "asserted aspect with relaxed key cardinality"; open whether anything resists that. Sharpened in `04-naming-layer.md` under *Threads under exploration*.
- **Name structure: leaf-names independent of path.** Whether the leaf segment is its own identity, or whether leaf-linking is an editing-layer rename UX over a flat namespace. Sharpened in `04-naming-layer.md` under *Threads under exploration*.

## Interfaces

- **First editor-like interface.** Phase 1 (`09-roadmap.md`) picks among batch runner, REPL, or stateful CLI. Once we're past minimal interfaces, what's the first editor-shaped one — scratch-buffer-style, structured editor, notebook, something else? Open.
- **What does the substrate API look like?** TBD; concrete signatures in `06-architecture.md` once the tech stack is picked.
- **Draft-state transition for hole-aware languages.** When we add hole-aware languages, interfaces offering drafts in those languages may store programs-with-holes directly rather than managing interface-side draft state. How do those interfaces coexist with interfaces still using the draft-state-is-interface-state model for non-hole-aware languages? Do we need a unified API shape that covers both?
- **Projectional output.** Some way of assigning special views for specific types that render in the browser instead of plain text. Examples: color swatches for a color type, charts for numeric arrays, images, SVG. Where does a viewer registration live — substrate aspect, interface-layer config, or namespace? How are viewers versioned? What is the fallback when no viewer is registered?
- **Documentation as an aspect.** Associate human-readable documentation with a term or type as an aspect; documentation itself may be hashed (in some documentation language — Markdown, structured prose, or something with embedded term references) and stored as a first-class definition. Documentation should be viewable in the browser detail pane. Open: what is the documentation language; is it asserted or can it be derived; how does documentation survive when a term is rebound (it is attached to the old hash, not the name)?
- **Update strategies.** Pin / follow / explicit migration recast as points in a 2-axis (scope × user-in-loop) space; substrate primitives (reverse-DAG query, atomic multi-rebind, `follow-clean` aspect, append-only binding history) identified. Sharpened in `04-naming-layer.md` under *Threads under exploration*. Still open: what gesture preserves a mint mark across edits (entangled with §"Minted identity" below); whether `follow-clean` is a stored aspect or only session-computed; whether a patch (the unit of co-dependent edits) eventually becomes a content-addressed artifact; how rules-and-filters layer on top of per-site toggles for partial cascades.
- **Projectional editing.** The dual of projectional output — richer, bidirectional editor widgets for specific types. A color picker for a color literal, a number slider for a numeric constant, a form for a record type. What is the protocol between a widget and the substrate — does the widget emit a new hash, or a surface-language fragment that goes through normal ingest? How do widgets coexist with the text-based editor?
- **Notebooks.** Interface mode interleaving text cells and program cells. Minimum: a text cell (free prose), a binding cell (sets a name → hash, like the current editor), and an eval cell (evaluates an expression and shows output). Open: is a notebook itself a content-addressed artifact; how are cells ordered; what is the re-evaluation granularity when an upstream binding changes; does a binding cell publish to the global namespace, a notebook-scoped namespace, or both?
- **Editing context.** A "checked-out context" — a set of bindings the user is treating as simultaneously in-flight before any are committed to the namespace. Live display (type feedback, evaluation, probes) assumes all checked-out bindings are updated together atomically. Enables co-dependent edits: if `f` calls `g` and both change together, both type-check against each other's new definitions. Open: what is the granularity of a context; how does committing work; how does the UI surface context vs. committed state; relationship to a notebook's cell scope; relationship to Grove-style collaborative editing.

## Minted identity

Sharpened in `10-minted-identity.md`.

- **Per-definition vs. per-language opt-in.** Unison-style `unique` per definition, a language-wide declaration that all its definitions are minted, or both with the per-language default overridable per-definition. **Answered-by-example 2026-08-07** (source read, `../systems/unison/04-caching-update-merge.md` §"Minting"): Unison takes a third option the framing above omits — **per-sort**, minting types and never terms, with the mint *on* by default and `structural` as the marked opt-out (`DeclParser.hs:230`). That is where arbor already converged in practice (p16/p17 mint only labels, p12 mints `Opaque` types). Still open as a *decision*; no longer open as a question about what the alternatives are.
- **Mint stability under merge.** *(New 2026-08-07, from the source read.)* A mint has to survive re-saving the definition it marks, and — once branching exists — has to not diverge when two branches edit the same definition independently. p11's explicit *edit-of-X* gesture answers the first. Nothing answers the second. Unison, which has no gesture and reconstructs the mint *by name* at save time, needed a dedicated `namespace_unique_type_guid` side table plus a `makeUniqueTypeGuids` pass to survive merge, and still resolves ties by choosing *"an arbitrary one"* when the name is conflicted. Whatever arbor does here is a substrate question, not an editing-layer one, and it lands on the mint/thread rung in `formalism/open-questions.md`.
- **Marks across content edits.** Whether a mint mark dies with its hash (blocks coincidental collapsing, nothing more) or survives edits (gives the substrate a second identity axis and a home for editing history / update propagation). Entangled with the Grove direction in `07-hazel-substrate.md`. **p12 finding (2026-06-04):** the mint plays two separable roles — *distinctness* (wants a fresh mark; dies-with-hash) and *lineage thread* (the survives-edits axis). Abstract-type soundness depends on neither — it rides witness-in-hash — and within a single checkout lineage is carried by the namespace, so p12 leans **dies-with-hash by default**, with survives-edits load-bearing only across checkouts/branches (collaboration phase). Does not retract p11's update-strategies use of marks-survive; scopes it. Sharpened in `10` §"Marks that survive content edits."
- **How marks are minted.** Random UID, monotonic counter, content-derived from creation context, something else. Affects reproducibility under re-ingest and import.
- **Where the mint mark lives in `Definition.t`.** First-class field with a sentinel for structural, a separate constructor, or an aspect with a hash-stable contract.
- **Interface surfacing.** Badge, color, nothing — bound up with the editing gesture in the per-definition reading.

## Type abstraction

Sharpened in `12-type-abstraction.md`. Substrate leanings are settled in several places (abstract-type identity = `opaque ++ mint ++ witness`; witness-in-hash forced by soundness; mint for distinctness; signature = binder over a `11` label-record; sealing in the type system; functor application applicative by default; projection inlines to a direct reference for fine-grained dependency; private = signature omission). What's open:

- **Opacity enforcement mechanism.** The *opacity trilemma* (flat-&-unbundled / pure-content revalidation / enforced opacity — pick two) means adversarial-safe enforcement without bundling needs an out-of-store capability. Near-term lean (2026-06-04): **editor-enforced opacity** for a cooperative threat model — flat, unbundled, pure-content `open #A in E : T` nodes; the editor offers the unfold affordance only within an abstract type's implementation set (not the namespace, not a stored bundle); an optional aspect surfaces unsanctioned opens. Deferred path to ingest-level / adversarial safety: **mint-as-keypair** (public half = the distinctness mint in `#A`'s hash; secret half = capability) with a deterministic-signature attestation aspect ingest verifies. Cryptographic safety not pursued now. Also resolves a latent tension in `12`'s §"Opacity is a typing discipline" (seals as independent dependable nodes vs. "not independently-ingestable"). Sharpened in `12-type-abstraction.md` §"Unbundled abstract types and the opacity trilemma."
- **Module ↔ namespace relationship.** Module-aware namespace with inlined projection (current lean) vs. reify-on-demand vs. first-class path-dependent access into namespaces. The display/round-trip contract and the gesture distinguishing "use this module's member" from a plain named reference are open.
- **Open vs. closed existential scope.** Path-dependent `m.t` by hash (lean) vs. OCaml-style unpack-into-binding vs. open existentials (Montagu–Rémy / avoidance problem). Not settled.
- **Signature/translucency encoding.** Node shape for per-component opaque/manifest signatures; how value-component types reference type-component labels by hash in a self-referential record.
- **First-class signature matching.** Coercion (restricted-module, new hash) vs. a subtyping judgment; whether depth/variance is ever needed. Inherits the row-variable question from "Label sort."
- **Functor application identity.** Applicative-by-default contract: editor-authored `F(X)` (mints) vs. computed `F(X)` (content-addressed), plus the explicit-unit generative escape hatch. Pin when a prototype forces it.
- **Same-witness-type invariant drift.** The criterion-6 boundary — changes preserving the witness type but altering its invariant are uncaught (general semantic drift, not abstraction-specific).
- **Mint-persistence across representation change (pair-counter lineage).** ~~Carry the mint forward via an edit-of gesture.~~ p12 finding (2026-06-04): not needed for the type system — witness-in-hash carries soundness, a fresh mark gives distinctness, and within-checkout lineage is carried by the namespace. Dropped from p12 (dies-with-hash); deferred to the cross-checkout/collaboration phase. See `10` §"Marks that survive content edits."
- **Editing / checkout UX.** What makes multi-version abstract modules legible to a user who never sees hashes. For a later interface prototype; relates to the "Editing context" item under "Interfaces."
- **Recursive modules.** Inherited from "Label sort"; intersects "Mutual recursion canonicalization" under "Content addressing."

## Related work

Raised by the literature sweep recorded in `../related-work/` (2026-08-03) and the Unison source read recorded in `../systems/unison/` (2026-08-07). Each of these is a question the survey surfaced, not a citation gap.

- **Is arbor accumulating exactly what Unison spent three years deleting?** *(New 2026-08-07.)* Between 2024 and 2025 Unison removed metadata links, `Patch`/`propagate`, and its SQL name-lookup index — roughly 5,950 lines — replacing each with derivation-on-demand or naming convention. arbor is currently building all three categories: aspects, reified edit history plus mints and threads, and derived indices. The narrow readings are filed separately (aspects under §"Associated data", mint upkeep under §"Minted identity"), but the pattern is worth naming as one question, because the three deletions are the same move. Two things cut *for* arbor and should be said in the same breath: the index Unison deleted was **forward**-derivable (names, recomputable by traversal memoized on subtree hashes) while it *kept* its reverse one (dependents) — and `Store.callers_of` is the reverse kind; and `Patch` is what binding history becomes only if it gains the ability to be *applied*, which arbor's `H` deliberately does not have. Open: is the distinction between "reified because it is expensive to recompute" and "reified because it records intent that cannot be recomputed at all" the right line, and does every piece of arbor's side-structure sit on one side of it? Sourced in `../systems/unison/05-deletions.md`.

- **Hash-typed abstract types as prior art.** Sewell's line — "Modules, Abstract Types, and Distributed Versioning" (POPL 2001), "Global Abstraction-Safe Marshalling with Hash Types" (ICFP 2003), Acute (ICFP 2005), HashCaml (ML 2006) — generates abstract-type names *freshly and by hashing*, so type equality alone protects abstraction invariants across a distributed system, with the soundness argument for putting the witness in the hash already worked out. That is `12-type-abstraction.md`'s `opaque ++ mint ++ witness` twenty years earlier, motivated by marshalling rather than by a content-addressed store; and POPL 2001 is specifically about abstract-type identity *across versions of independently-compiled programs*, which is no-silent-breakage in a different setting. Open: what does p12's construction add beyond a change of motivation, and does arbor inherit their soundness argument or need its own? Sourced in `../related-work/03-modules-abstraction.md` §"Hashing abstract types across a distributed codebase — the Sewell cluster".
- **`Ill_typed` rejects ingest.** p9 onward, a term that fails to type-check is refused at the Store boundary. That contradicts two things at once: the marked-lambda-calculus totality result (Zhao et al., POPL 2024) says *every* expression can be given a meaning, and arbor's own posture is commit-and-report with visible breakage rather than gating. Open: is abort-at-ingest a substrate invariant or editing-layer policy that leaked into the Store? If the latter, what does the Store record for an ill-typed term, and what does `Type_of` mean for it? Touches `02-definitions-and-derived-data.md` and `03-content-addressing.md` §"Non-goals". Sourced in `../related-work/02-structure-editors.md`.
- **Aspect eviction.** Derived entries are valid forever, which converts a correctness problem into an unbounded-growth one. Hammer & Acar (ISMM 2008) is the citation for why that hurts in practice. Nothing in `02-definitions-and-derived-data.md` addresses eviction, and the bootstrap-accepts-full-rebuilds posture papers over it rather than answering it. Open: is eviction a Store concern, an Attachment concern, or deliberately out of scope until volume forces it? Sourced in `../related-work/04-incrementality.md`.
- **Namespace as a replicated tree.** Hierarchical dotted names (p9 onward) under concurrent writers — agents especially — is a replicated tree with moves and renames, and Kleppmann et al. ("A Highly-Available Move Operation for Replicated Trees," IEEE TPDS) demonstrate that Google Drive and Dropbox get this wrong and give a correct algorithm. `00-overview.md:39` defers branching and merging, but *agentic concurrency arrives before branching does*, and the failure mode is silently losing bindings — the exact thing the naming layer exists to prevent. Open: does the namespace need a convergent datatype before multi-agent use, or does commit-and-report with visible residuals suffice? Sourced in `../related-work/05-naming-versioning.md`.
- **Positioning against write-time mediation.** STORM (arXiv:2605.20563) solves concurrent agent edits by mediating access to a shared workspace so conflicts are detected *at write time*, explicitly against git-worktree-per-agent, and beats worktree baselines on Commit0-Lite. It uses no content addressing at all. Meanwhile cheap forking is already an engineered OS primitive with sub-350 µs branch creation (arXiv:2602.08199), and 100% structural convergence still leaves 5–10% semantic conflicts (arXiv:2510.18893). Open: what does definition-level immutability buy over mediation, stated as something falsifiable? The one claim the survey found unclaimed is hash-keyed type-and-test caching as the substrate for agent *speculation* — results already computed before any name is rebound. Sourced in `../related-work/08-agentic-vc.md`.
