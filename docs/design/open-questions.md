## Associated data

- **Is the asserted/derived split load-bearing rather than descriptive?** *(2026-08-07, from the Unison source read.)* Unison built nearly this mechanism: extensible per-definition metadata, categories identified by convention, values that were content-addressed references, all hashed into the namespace. It deleted it in January 2024. Its motivating categories went separate ways. API docs became a naming convention (`foo.doc`). "Is this a test" became a type query (a test is any term of type `[Test.Result]`). Author, copyright holder and license went nowhere and are now unattached definitions under `metadata.*`. Creation date and subpath comments were never built. The categories keyed by hash and written by the system (the type index, the dependents index, the evaluation cache) all survived and grew. The discriminator is key shape, not assertedness. What died was keyed by (definition, name), so it duplicated the namespace without inheriting its aliasing, merge, history or suffix resolution. All of arbor's aspects are of the surviving shape (`Type_of`, `has-holes:v1`, `follow-clean:v1`, translation targets, the eval cache). Open: should `02-definitions-and-derived-data.md` weight the two halves instead of treating them symmetrically? Is an author-asserted, name-shaped fact better stored as a definition with a name? If so, where do the categories that then have no home go, given that Unison dropped them silently? One of Unison's forces, membership in the namespace hash (which makes annotating a structural change), does not apply to arbor, whose aspects sit outside Σ's hash by construction. `02` should say so explicitly. Argued in `../systems/unison/09-side-structure.md`; the reasons given there are inferred from evidence, not stated by Unison.
- **Vocabulary for "aspect."** Chosen provisionally to avoid the TAPL kind collision. Alternatives if it causes friction: *facet*, *annotation*, *attribute*, *channel*.
- **Conflict handling.** When an asserted entry and a derived entry disagree on one property (the annotation says `Int→Int`, inference says `Bool→Bool`), the substrate records both. What is the default surface behaviour?
- **Where aspect descriptors live.** Per-language module, global registry, or both? This has large practical consequences for the tech stack.
- **Cross-aspect dependencies.** Evaluation depends on types; translation may depend on elaboration. Formalize an aspect-dependency graph, or handle it ad hoc in each procedure?
- **History of asserted entries.** Names and descriptions change. Is edit history kept, and at what granularity? Ties into branching; see also "Unifying namespace and aspect-store lifecycles" under Naming layer.
- **Graduating from tag+version to content-addressed procedures.** What triggers the migration? Probably a stable meta-language candidate plus enough cached derived entries to justify precise invalidation.

## Content addressing

Closed in `03-content-addressing.md`:
- ~~Canonicalization.~~ Syntactic by default, α-equivalence at minimum, per-language declarations allowed. Coarser semantic equivalences are per-language opt-ins, left open.
- ~~Primitive / builtin identity.~~ Manually versioned tags, the same model as procedure identity.

Still open:
- **Mutual recursion canonicalization.** A language with mutually recursive definitions needs a way to close the cycle. As of 2026-08-07 there are three options and none is chosen. (A) Unison's component: hash the group as one object and address members by index. This changes `Σ`'s type to `Hash ⇀ Node⁺` and refuses ingest when two members are structurally identical modulo intra-group references. (B1) A fixpoint over a positional tuple, with members as projections. `Σ` is unchanged, no mints are needed, and p17's `Pair`/`Fst`/`Snd` are reused. The bundle hash is invariant under group automorphisms, so the bad case costs only an arbitrary but behaviour-preserving choice of which projection is which: a coincidental non-collapse instead of a rejected ingest. (B2) The same over a labeled record. This restores presentation-independence in that case by turning the canonicalization question into a name-keyed mint-stability question; it does not dissolve it. The real choice is between a mint and a rare loss of presentation-independence. Worked through in `03-content-addressing.md` §"Mutual recursion: three ways to close the cycle", which also notes that canonically ordering a recursive group is graph canonization, so no cleverer hash removes (A)'s failure. This entry named only (A) before 2026-08-07. Not urgent. Recursive modules (under Label sort and Type abstraction) intersect this item.
- **Holes and incomplete programs.** If the substrate hashes incomplete programs (Hazel-style editing), how do holes enter the canonical form? Unique hole identities, subsumption-style matching, or something else?
- **Cross-version primitive aliasing.** If `int:add:v1` and `int:add:v2` differ only cosmetically, callers of v1 are orphaned. Is there an aliasing story, or is this an accepted cost?
- **Hashing types as well as terms.** Types are inline in term encodings; p6 hashes types only to encode procedure ids, not as definitions. First-class content-addressed types would give type aliasing through the namespace and change how `Type_of(...)`-shaped aspect values are stored. Sharpened in `03-content-addressing.md` under *Threads under exploration*.
- **Hash algorithm.** Not fixed; bootstrap accepts full rebuilds. The choice will be made when one is needed.

## Naming layer

- **Scope of names.** Per user, per workspace, global? Unison uses namespaces. We want to defer structure without painting ourselves into a corner.
- **Dependency-depth priority in suffix resolution.** *(2026-08-07, from the Unison source read.)* p9, p10 and p17 resolve a bare suffix only when it is unambiguous and report `Ambiguous` otherwise. Unison adds a rule arbor lacks: names nested more deeply beneath a `lib` segment lose ties, so `map` resolves to `lib.base.List.map` even though `lib.something.lib.base.Set.map` also ends in `map` (`unison-core/src/Unison/Name.hs:597-599`). Without such a rule, vendoring a dependency that itself vendors a dependency makes every common suffix ambiguous. Open: is depth priority an editing-layer resolution policy or a substrate property of the namespace, and does it require the substrate to treat some segments (`lib`) as special? Sourced in `../systems/unison/03-namespace-and-history.md` §"Suffix resolution".
- **Names that denote things with no hash.** *(2026-08-07, from the Unison source read.)* Unison distinguishes `Reference` (a definition) from `Referent` (what a term-position name may denote: a term or a data/effect constructor). A constructor has no hash of its own; it is addressed as (declaring type's hash, ordinal). So `Maybe.Just` names something that is not a stored definition. arbor's namespace maps names to hashes and nothing else. p16's label sort answers an adjacent question differently: a label is a stored definition with its own hash. Open: when a substrate language gains datatypes with constructors, do constructors become definitions (arbor's label answer) or relative references (Unison's answer), and must `N`'s codomain widen? Sourced in `../systems/unison/03-namespace-and-history.md` §"Referent vs Reference".
- **Name → hash resolution timing.** Only at edit time, or also at a "load" step for interfaces?
- **Unifying namespace and aspect-store lifecycles.** When branching arrives, does a shared "container" make sense, or do the two stay parallel? See the cross-reference sections in `02` and `04`.
- **Name structure: hierarchical paths.** Editing-layer convention, substrate-aware paths, or a substrate-fixed format? Bound up with when namespace branching enters scope. Sharpened in `04-naming-layer.md` under *Threads under exploration*.
- **Name structure: tags.** Many-to-many name-shaped attachments. The tentative reading is an asserted aspect with relaxed key cardinality; open whether anything resists that. Sharpened in `04-naming-layer.md` under *Threads under exploration*.
- **Name structure: leaf-names independent of path.** Is the leaf segment its own identity, or is leaf-linking an editing-layer rename UX over a flat namespace? Sharpened in `04-naming-layer.md` under *Threads under exploration*.

## Interfaces

- **First editor-like interface.** Phase 1's choice among batch runner, REPL and stateful CLI is tracked under Roadmap. Past minimal interfaces, what is the first editor-shaped one: scratch buffer, structured editor, notebook, something else?
- **What does the substrate API look like?** To be decided; concrete signatures go in `06-architecture.md` once the tech stack is picked.
- **Draft-state transition for hole-aware languages.** Interfaces offering drafts in a hole-aware language may store programs-with-holes directly instead of keeping draft state in the interface. - **Projectional output.** Type-specific views rendered in the browser instead of plain text: color swatches for a color type, charts for numeric arrays, images, SVG. Where does a viewer registration live: substrate aspect, interface-layer config, or namespace? How are viewers versioned? What is the fallback when none is registered?
- **Projectional editing.** The dual of projectional output: bidirectional editor widgets for specific types, such as a color picker for a color literal, a slider for a numeric constant, a form for a record type. What is the protocol between widget and substrate? Does a widget emit a new hash, or a surface-language fragment that goes through normal ingest? How do widgets coexist with the text editor?
- **Documentation as an aspect.** Attach human-readable documentation to a term or type as an aspect. The documentation may itself be a hashed, first-class definition in some documentation language (Markdown, structured prose, or something with embedded term references), viewable in the browser detail pane. Open: what is the documentation language? Is it asserted, or can it be derived? How does documentation survive a rebind, given it is attached to the old hash and not the name?
- **Update strategies.** Pin, follow and explicit migration recast as points in a two-axis (scope × user-in-loop) space, with substrate primitives identified: a reverse-DAG query, atomic multi-rebind, the `follow-clean` aspect, append-only binding history. Sharpened in `04-naming-layer.md` under *Threads under exploration*. Still open: which gesture preserves a mint mark across edits (entangled with Minted identity below); whether `follow-clean` is a stored aspect or computed per session; whether a patch, the unit of co-dependent edits, becomes a content-addressed artifact; how rules and filters layer over per-site toggles for partial cascades.
- **Notebooks.** An interface mode interleaving text cells and program cells. Minimum: a text cell (free prose), a binding cell (sets a name → hash, like the current editor), and an eval cell (evaluates an expression and shows the output). Open: is a notebook a content-addressed artifact? How are cells ordered? What is the re-evaluation granularity when an upstream binding changes? Does a binding cell publish to the global namespace, a notebook-scoped one, or both?
- **Editing context.** A checked-out context: a set of bindings the user treats as in flight together before any is committed to the namespace. Live display (type feedback, evaluation, probes) assumes all checked-out bindings update together atomically. This enables co-dependent edits: if `f` calls `g` and both change, each type-checks against the other's new definition. Open: the granularity of a context; how committing works; how the UI distinguishes context from committed state; the relationship to a notebook's cell scope and to Grove-style collaborative editing. Expanded on 2026-08-19 into `13-editing-context.md`, with the literature in `../related-work/12-editing-contexts.md` and a source read of Unison's scratch file in `../systems/unison/11-scratch-file.md`. ## Minted identity

Sharpened in `10-minted-identity.md`.

- **Per-definition vs. per-language opt-in.** Unison-style `unique` per definition, a language-wide declaration that all definitions are minted, or both with a per-language default overridable per definition. Answered by example on 2026-08-07 (`../systems/unison/04-caching-update-merge.md` §"Minting"): Unison takes a third option, per sort. It mints types and never terms, with minting on by default and `structural` as the marked opt-out (`DeclParser.hs:230`). arbor has converged there in practice (p16/p17 mint only labels; p12 mints `Opaque` types). The alternatives are now known; the decision remains open.
- **Mint stability under merge.** *(2026-08-07, from the source read.)* A mint must survive re-saving the definition it marks and, once branching exists, must not diverge when two branches edit the same definition independently. p11's explicit edit-of-X gesture answers the first requirement. Nothing answers the second. Unison has no gesture and reconstructs the mint by name at save time. It needed a dedicated `namespace_unique_type_guid` side table and a `makeUniqueTypeGuids` pass to survive merge, and when the name is conflicted it still picks "an arbitrary one". A second data point (2026-08-19): jj has the same axis, a change ID that tracks a commit across rewrites, and resolves it differently. It mints once at random, never re-derives, and treats one change with several visible commits as a labeled divergent state, not an error. It pays the same cost, a `StackedTable` side file at `.jj/repo/store/extra/`, because the change ID sits outside the commit hash (`../systems/jj/03-change-ids-and-conflicts.md`). Two independent systems put identity outside the hash and both built a side table. arbor's mint-in-the-hash avoids the table and takes on the opposite problem. This is a substrate question, and it lands on the mint/thread rung in `formalism/open-questions.md`.
- **Marks across content edits.** Does a mint mark die with its hash (blocking coincidental collapse and nothing more), or survive edits (giving the substrate a second identity axis and a home for editing history and update propagation)? Entangled with the Grove direction in `07-hazel-substrate.md`. p12 finding (2026-06-04): the mint plays two separable roles, distinctness (wants a fresh mark; dies with the hash) and lineage thread (survives edits). Abstract-type soundness depends on neither, since it rides witness-in-hash, and within a single checkout the namespace carries lineage. So p12 leans dies-with-hash by default, with survives-edits load-bearing only across checkouts or branches (the collaboration phase). This scopes p11's update-strategies use of surviving marks without retracting it. It also closes the type-abstraction question of carrying a mint across a representation change (the pair-counter lineage), which p12 dropped and deferred to the collaboration phase. Sharpened in `10` §"Marks that survive content edits."
- **How marks are minted.** Random UID, monotonic counter, derived from creation context, something else. Affects reproducibility under re-ingest and import.
- **Where the mint mark lives in `Definition.t`.** A first-class field with a sentinel for structural definitions, a separate constructor, or an aspect with a hash-stable contract.
- **Interface surfacing.** Badge, color, nothing. Bound up with the editing gesture in the per-definition reading.

## Type abstraction

Sharpened in `12-type-abstraction.md`. Several substrate leanings are settled: abstract-type identity is `opaque ++ mint ++ witness`; soundness forces witness-in-hash; the mint gives distinctness; a signature is a binder over a `11` label-record; sealing lives in the type system; functor application is applicative by default; projection inlines to a direct reference for fine-grained dependency; private means omitted from the signature. Open:

- **Opacity enforcement mechanism.** The opacity trilemma (flat-and-unbundled, pure-content revalidation, enforced opacity: pick two) means adversarial-safe enforcement without bundling needs a capability outside the store. Near-term lean (2026-06-04): editor-enforced opacity under a cooperative threat model. Nodes are flat, unbundled, pure-content `open #A in E : T`. The editor offers the unfold affordance only within an abstract type's implementation set (not the namespace, not a stored bundle). An optional aspect surfaces unsanctioned opens. The deferred path to ingest-level, adversarial safety is mint-as-keypair: the public half is the distinctness mint in `#A`'s hash, the secret half is the capability, and ingest verifies a deterministic-signature attestation aspect. Cryptographic safety is not pursued now. This also resolves a latent tension in `12`'s §"Opacity is a typing discipline" between seals as independent dependable nodes and "not independently-ingestable". Sharpened in `12-type-abstraction.md` §"Unbundled abstract types and the opacity trilemma."
- **Module ↔ namespace relationship.** A module-aware namespace with inlined projection (current lean), reify-on-demand, or first-class path-dependent access into namespaces. Open: the display and round-trip contract, and the gesture that distinguishes "use this module's member" from a plain named reference.
- **Open vs. closed existential scope.** Path-dependent `m.t` by hash (lean), OCaml-style unpack into a binding, or open existentials (Montagu–Rémy; the avoidance problem). Not settled.
- **Signature/translucency encoding.** The node shape for per-component opaque/manifest signatures, and how value-component types reference type-component labels by hash in a self-referential record.
- **First-class signature matching.** Coercion (a restricted module with a new hash) or a subtyping judgment; whether depth or variance is ever needed. Inherits the row-variable question from Label sort.
- **Functor application identity.** The applicative-by-default contract: editor-authored `F(X)` mints, computed `F(X)` is content-addressed, and an explicit unit argument is the generative escape hatch. Fix when a prototype forces it.
- **Same-witness-type invariant drift.** The criterion-6 boundary: a change that keeps the witness type but alters its invariant goes uncaught. This is general semantic drift, not specific to abstraction.
- **Mint-persistence across representation change (pair-counter lineage).** ~~Carry the mint forward via an edit-of gesture.~~ Closed by the p12 finding (2026-06-04) recorded under Minted identity, "Marks across content edits".
- **Editing / checkout UX.** What makes multi-version abstract modules legible to a user who never sees hashes? For a later interface prototype; relates to "Editing context" under Interfaces.
- **Recursive modules.** See the entry under Label sort.

## Related work

Raised by the literature sweep in `../related-work/` (2026-08-03) and the Unison source read in `../systems/unison/` (2026-08-07). Each is a question the survey surfaced, not a citation gap.

- **Is arbor accumulating exactly what Unison spent three years deleting?** *(2026-08-07.)* Between 2024 and 2025 Unison removed metadata links, `Patch`/`propagate`, and its SQL name-lookup index, roughly 5,950 lines, replacing each with derivation on demand or a naming convention. arbor is building all three categories: aspects, reified edit history plus mints and threads, and derived indices. The narrow readings are filed under Associated data (aspects) and Minted identity (mint upkeep). The pattern is filed here as one question because the three deletions are the same move. Two facts favour arbor. The index Unison deleted was forward-derivable (names, recomputable by traversal memoized on subtree hashes), while it kept its reverse index (dependents), and `Store.callers_of` is a reverse index. And `Patch` is what binding history becomes only if it can be applied, which arbor's `H` cannot. Open: is the line between "reified because expensive to recompute" and "reified because it records intent that cannot be recomputed" the right one, and does every piece of arbor's side-structure fall clearly on one side? Sourced in `../systems/unison/05-deletions.md`.
- **Hash-typed abstract types as prior art.** Sewell's line generates abstract-type names freshly and by hashing, so type equality alone protects abstraction invariants across a distributed system: "Modules, Abstract Types, and Distributed Versioning" (POPL 2001), "Global Abstraction-Safe Marshalling with Hash Types" (ICFP 2003), Acute (ICFP 2005), HashCaml (ML 2006). The soundness argument for putting the witness in the hash is already worked out there. This is `12-type-abstraction.md`'s `opaque ++ mint ++ witness` twenty years earlier, motivated by marshalling instead of a content-addressed store. POPL 2001 specifically addresses abstract-type identity across versions of independently compiled programs, which is no-silent-breakage in another setting. Open: what does p12's construction add beyond a change of motivation, and does arbor inherit their soundness argument or need its own? Sourced in `../related-work/03-modules-abstraction.md` §"Hashing abstract types across a distributed codebase — the Sewell cluster".
- **`Ill_typed` rejects ingest.** From p9 on, a term that fails to type-check is refused at the Store boundary. This conflicts with the marked lambda calculus totality result (Zhao et al., POPL 2024), which gives every expression a meaning, and with arbor's commit-and-report posture of visible breakage over gating. Open: is abort-at-ingest a substrate invariant, or editing-layer policy that leaked into the Store? If the latter, what does the Store record for an ill-typed term, and what does `Type_of` mean for it? Touches `02-definitions-and-derived-data.md` and `03-content-addressing.md` §"Non-goals". Sourced in `../related-work/02-structure-editors.md`.
- **Aspect eviction.** Derived entries are valid forever, which turns a correctness problem into unbounded growth. Hammer & Acar (ISMM 2008) is the citation for why that hurts in practice. `02-definitions-and-derived-data.md` does not address eviction, and the bootstrap-accepts-full-rebuilds posture defers the question without answering it. Open: is eviction a Store concern, an Attachment concern, or out of scope until volume forces it? Sourced in `../related-work/04-incrementality.md`.
- **Namespace as a replicated tree.** Hierarchical dotted names (p9 on) under concurrent writers, agents especially, form a replicated tree with moves and renames. Kleppmann et al. ("A Highly-Available Move Operation for Replicated Trees," IEEE TPDS) show that Google Drive and Dropbox get this wrong and give a correct algorithm. `00-overview.md:39` defers branching and merging, but agentic concurrency arrives before branching, and the failure mode is silently lost bindings, which the naming layer exists to prevent. Open: does the namespace need a convergent datatype before multi-agent use, or does commit-and-report with visible residuals suffice? Sourced in `../related-work/05-naming-versioning.md`.
- **Positioning against write-time mediation.** STORM (arXiv:2605.20563) handles concurrent agent edits by mediating access to a shared workspace, detecting conflicts at write time. It argues against git-worktree-per-agent, beats worktree baselines on Commit0-Lite, and uses no content addressing. Cheap forking is already an engineered OS primitive, with branch creation under 350 µs (arXiv:2602.08199), and full structural convergence still leaves 5–10% semantic conflicts (arXiv:2510.18893). Open: what does definition-level immutability buy over mediation, stated falsifiably? The one claim the survey found unclaimed is hash-keyed type-and-test caching as the substrate for agent speculation, with results computed before any name is rebound. Sourced in `../related-work/08-agentic-vc.md`.
