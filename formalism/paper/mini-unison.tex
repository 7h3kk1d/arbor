\large A formal model of Unison's content addressing and update scheme}
\author{The arbor project}
\date{Draft --- \today}

\begin{document}
\maketitle

\begin{abstract}
Unison is the system \arborcore{} is closest to, and it has no publication. Its design claims ---
hashes as identity, names as metadata, caches that are never invalidated, no diamond-dependency
problem --- have never been formally stated, let alone proved. This document states them, for a
small object language, faithful to the implementation at a pinned commit.

It is a \emph{contrast} artifact, not a rung on the \arborcore{} $\to$ \arborstlc{} ladder: it models
another system and proposes nothing. Its purpose is to give arbor's choices something precise to be
different from, and its results are correspondingly comparative. Three are worth stating up front.
\textbf{(i)} Unison's store is not $\Hash \pfn \Node$ but $\Hash \pfn \Comp$, and this is not a
canonicalization detail but a change to the type of the store. \textbf{(ii)} Presentation-independence
of component hashing is \emph{conditional}, not absolute --- when two members of a recursive cycle
are structurally equivalent modulo intra-cycle references, the component's hash depends on the
members' \emph{names}; the condition is decidable, which is why the implementation detects it and
aborts rather than silently storing a name-dependent hash. \textbf{(iii)} Unison's \texttt{update} is
implemented by rendering definitions to source and re-parsing them, so its correctness rests on
print-then-parse preserving hashes --- a property the implementation never states and maintains with
a golden-file regression corpus. That property is \coreref{prop:print-elab}, proved.
\end{abstract}

\section{Scope and posture}\label{sec:uscope}

\subsection{What this document is}

A model of \emph{another system}. Every definition below is faithful to the Unison implementation at
commit \texttt{db60ce2} (2026-08-07), and every claim carries a margin tag naming the file and lines
it is faithful to. Cite \texttt{UnisonSource}, pinned to that commit, for any claim about how Unison
behaves; there is no publication to cite instead, which is the reason this document exists. The
prose source read this formalization rests on is \texttt{docs/systems/unison/}.

Nothing here is a proposal. Where a design of Unison's differs from arbor's, \cref{sec:contrast}
records the fork and what each side pays; it does not adjudicate.

\subsection{The object language, and why it is typed}

The object language is close to \arborcore{}'s: untyped $\lambda$-calculus, plus $\TNat$ and $\TText$
literals, plus references. It is then given \emph{simple types}, for one reason: Unison's
\texttt{update} re-typechecks, and the interesting half of \texttt{update} is what happens when
re-typechecking \emph{fails}. Without a type system that branch is unreachable and the sharpest
contrast in the document --- Unison evicts the broken definitions and hands them back as source,
where arbor commits and reports a residual (\stlcref{def:residual}) --- cannot be stated.

\subsection{Modeled}

\begin{itemize}[nosep]
  \item Named abstract binding trees, with de Bruijn indices computed only at hash time.
  \item Ingest of a \emph{binding group}, strongly-connected-component decomposition, and component
        hashing with its canonical ordering algorithm.
  \item $\Reference ::= \UBuiltin{\cdot} \mid \UDer{\cdot}{\cdot}$, and the asymmetry of reference
        transparency at position $0$.
  \item The type inside the term hash.
  \item The namespace as a \emph{relation}, with conflict a representable state and unconflictedness a
        derived predicate that operations demand.
  \item The watch cache: no invalidation, and a key that need not be a named definition.
  \item \texttt{update}: the dependents index, the scope computation, the pretty-print environment,
        render/parse/typecheck, and eviction on failure.
\end{itemize}

\subsection{Not modeled}\label{sec:unotmodeled}

Recorded so the boundary is stated rather than implied. Each is a candidate successor.

\begin{itemize}[nosep]
  \item \textbf{The namespace's representation.} Unison's \texttt{Branch} is a hashed Merkle tree of
        name segments whose \texttt{children} field points at each child's \emph{causal} hash, so
        every level has its own history \src{Hashing/V2/Branch.hs:22-39}. Here $\UNames$ is a bare
        relation. \Cref{sec:unaming} models the naming \emph{semantics}, which \texttt{update} needs;
        it does not model the object.
  \item \textbf{History, branching, merge.} \texttt{Causal} as a content-addressed DAG, and the merge
        algorithm.
  \item \textbf{Suffix resolution and the \texttt{lib}-depth priority rule.} Names here are atomic.
  \item \textbf{Data declarations and \texttt{unique}-type minting.} With only $\TNat$, $\TText$ and
        arrows there are no declarations, so the $\UCon{\cdot}{\cdot}$ arm of $\Referent$ is present
        but vestigial, and the whole minting axis is absent.
  \item \textbf{Synhash}, the propagation-provenance mechanism used by merge.
  \item \textbf{Abilities, the ANF runtime, \texttt{LocalIds} and the serialization layer.}
\end{itemize}

\section{Part I --- The object language}\label{sec:ulang}

\subsection{Terms, named}

\begin{definition}[Terms]\label{def:uterm}
\src{U/Core/ABT.hs:16-25} Fix a countable set of variables $x,y,z$ and a set of builtin names
$b \in \TText$.
\[
  t,u \;::=\; \uvar{x} \;\mid\; \ulam{x}{t} \;\mid\; \uapp{t}{u}
        \;\mid\; \unat{n} \;\mid\; \utext{s} \;\mid\; \uref{r} \;\mid\; \uann{t}{T}
\]
where $r \in \Reference$ (\cref{def:uref}). Binders carry \emph{names}, and those names are stored.
$\uann{t}{T}$ is a type annotation; it is a term former because \cref{def:typeinhash} needs a place
to put a type inside a term.
\end{definition}

\begin{remark}[Names in storage --- the first fork]\label{rem:names}
\arborcore{} stores de Bruijn terms and reconstructs names for display (\coreref{def:core}). Unison
stores names and computes de Bruijn indices only while hashing (\cref{def:uhash}). The choice is
usually presented as taste. It is not: \cref{sec:uupdate}'s \texttt{update} renders stored
definitions back to source that a human must read and a parser must resolve, and it is the
\emph{author's} binder names that survive into that rendering. \arborcore{}'s round trip is stated
only up to name choice (\coreref{prop:elab-print}) precisely because it does not keep them.
\end{remark}

\begin{definition}[$\alpha$-equivalence]\label{def:ualpha}
\src{U/Core/ABT.hs:49-60} $t \equiv_\alpha u$ is the least congruence identifying
$\ulam{x}{t}$ with $\ulam{y}{t[x := y]}$ for $y$ fresh in $t$. Implemented by renaming aligned
binders to a common fresh variable; it is the \texttt{Eq} instance, so $\alpha$-equivalent terms are
\emph{equal} in the implementation even before hashing.
\end{definition}

\subsection{Types}

\begin{definition}[Types and typing]\label{def:utyping}
\[
  T,U \;::=\; \TNat \;\mid\; \TText \;\mid\; \uarr{T}{U}
\]
A context $\Gamma$ maps variables to types; a \emph{signature} $\Delta$ maps references to types
(for builtins, given; for derived references, read off the store by \cref{def:typeinhash}).
Syntax-directed, with no inference:
\begin{mathpar}
  \inferrule*[right=U-Var]{\Gamma(x) = T}{\utypes{\Gamma}{\uvar{x}}{T}}
  \and
  \inferrule*[right=U-Nat]{\ }{\utypes{\Gamma}{\unat{n}}{\TNat}}
  \and
  \inferrule*[right=U-Text]{\ }{\utypes{\Gamma}{\utext{s}}{\TText}}
  \\
  \inferrule*[right=U-Abs]{\utypes{\Gamma, x{:}T}{t}{U}}{\utypes{\Gamma}{\ulam{x}{t}}{\uarr{T}{U}}}
  \and
  \inferrule*[right=U-App]{\utypes{\Gamma}{t}{\uarr{T}{U}} \\ \utypes{\Gamma}{u}{T}}
                          {\utypes{\Gamma}{\uapp{t}{u}}{U}}
  \\
  \inferrule*[right=U-Ref]{\Delta(r) = T}{\utypes{\Gamma}{\uref{r}}{T}}
  \and
  \inferrule*[right=U-Ann]{\utypes{\Gamma}{t}{T}}{\utypes{\Gamma}{\uann{t}{T}}{T}}
\end{mathpar}
\end{definition}

\begin{remark}[\textsc{U-Ref} reads $\Delta$, not the store]\label{rem:uref-delta}
Contrast \stlcref{def:typing}'s \textsc{T-Ref}, whose premise is the \emph{target's typing
derivation}, so a well-typed term carries its support with it. Here the type of a reference is looked
up, and it is available without re-deriving anything because the type is \emph{inside the hash}
(\cref{def:typeinhash}): a stored definition's type cannot be stale, because changing it would change
the definition's identity. The two systems buy the same locality by opposite means.
\end{remark}

\subsection{Binding groups}

\begin{definition}[Binding group]\label{def:bindgroup}
\src{Hashing/V2/ABT.hs:106-134} A \emph{binding group} is a finite map
$\bg : \Name \pfn \Term$ whose members' free variables all lie in $\dom(\bg)$. Ingest takes a binding
group, not a term.
\end{definition}

\begin{remark}[Where mutual recursion lives]\label{rem:mutrec}
Unison has no recursive term former in the surface language for this purpose: mutual recursion is
just several top-level bindings that mention each other, and \texttt{hashComponents} is the operation
that takes the whole map. Modeling ingest at the group rather than the term is therefore both
faithful and cheaper than adding $\mathsf{letrec}$ --- and it is what makes \cref{sec:ustore}'s
components non-trivial. The implementation \emph{errors} if the group has free variables it cannot
bind \src{ABT.hs:128-134}, which is why \cref{def:bindgroup} makes closedness part of being a group.
\end{remark}

\section{Part II --- The store, components, and the hash}\label{sec:ustore}

\subsection{References}

\begin{definition}[Reference]\label{def:uref}
\src{U/Codebase/Reference.hs:77-119}
\[
  r \in \Reference \;::=\; \UBuiltin{b} \;\mid\; \UDer{h}{i}
  \qquad b \in \TText,\; h \in \Hash,\; i \in \Pos = \mathbb{N}
\]
\end{definition}

\begin{remark}[Builtins are named extrinsically]\label{rem:builtin}
$\UBuiltin{b}$ carries a \emph{text name}, not a hash. So the identity of a primitive is an assertion
by the implementation, not a derivation from its content --- extrinsic in exactly the sense
\texttt{docs/related-work/01-content-addressing.md} takes from the Software Heritage identifier work.
Unison is intrinsically identified everywhere \emph{except} at its primitives, and the boundary is
visible in the type. arbor makes the same trade with a different mechanism, manually-versioned
procedure tags (\texttt{docs/design/decisions.md} 2026-04-20), and the same observation applies: the
hash chain has to bottom out somewhere, and wherever it bottoms out is extrinsic.
\end{remark}

\begin{definition}[Referent]\label{def:ureferent}
\src{U/Codebase/Referent.hs:18-30} $\Referent ::= \URefT{r} \mid \UCon{r}{k}$. Names denote
referents, not references: a name may denote a data constructor rather than a definition. With no
data declarations in scope (\cref{sec:unotmodeled}) the second arm is vestigial here, and is retained
only so \cref{sec:unaming} has the right shape.
\end{definition}

\subsection{The store}

\begin{definition}[Component and store]\label{def:ustore}
\src{U/Codebase/Reference.hs:114-119; docs/repoformats/v2.markdown} A \emph{component} is a non-empty
finite sequence of terms, $\Comp = \Term^{+}$. The store is
\[
  \UStore : \Hash \pfn \Comp .
\]
A definition is addressed by a \emph{pair}: $\UDer{h}{i}$ denotes the $i$-th member of the component
at $h$. A non-recursive definition is a singleton component with $i = 0$.
\end{definition}

\begin{remark}[This is a different type of store]\label{rem:storetype}
\coreref{def:store} is $\Store : \Hash \pfn \Node$, and \coreref{def:refs}, $\wf$'s no-dangle clause,
$\callers$, and $\rho$ are all stated over it. Replacing $\Node$ by $\Comp$ and a hash by a pair
moves every one of them. \texttt{docs/design/03-content-addressing.md} formerly described Unison's
approach as supplying ``a canonical ordering for the group''; that understates it twice, once because
the commitment is to the store's type and not to an ordering, and once because the ordering is not
unconditionally available (\cref{thm:ordering}).
\end{remark}

\subsection{Hashing}

\begin{definition}[Token stream]\label{def:tokens}
\src{Tokenizable.hs:122-137} Nothing is hashed as raw bytes. The hash input is a tagged,
length-prefixed token stream: $\mathsf{Tag}$ is one byte; $\mathsf{Text}$ and $\mathsf{Bytes}$ are a
64-bit big-endian length followed by the payload; $\mathsf{Nat}$ is 64-bit big-endian;
$\mathsf{Hashed}$ is a fixed-width hash with no length prefix. Every stream begins with a
\emph{version} token, and each syntactic layer begins with a tag that domain-separates it from the
others \src{Term.hs:147-152}. We write $\mathsf{acc}(\overline{\tau})$ for the hash of a token list.
\end{definition}

\begin{remark}[Versioning instead of rebuilding]\label{rem:version}
The version token exists so that changing the hash function changes \emph{every} hash, and the schema
carries a many-hashes-to-one-object table so old references keep resolving under an old scheme
\src{sql/create.sql:33-49}. arbor's stated answer to the same question is to accept full state
rebuilds. Recorded as prior art, not as a defect on either side.
\end{remark}

\begin{definition}[Hashing a term]\label{def:uhash}
\src{Hashing/V2/ABT.hs:143-172} Hashing carries an environment
$\HEnv \in (\wp(\Name) + \Name)^{*}$, innermost first: $\mathsf{R}(x)$ is an ordinary binder and
$\mathsf{L}(V)$ is a \emph{cycle frame} naming a whole set at once. Write $\uhash{\HEnv}{t}$.
\begin{align*}
  \uhash{\HEnv}{\uvar{x}}    &= \mathsf{acc}[\mathsf{Nat}\; j]
     && \text{$j$ least with $x \in \HEnv_j$; undefined if none}\\
  \uhash{\HEnv}{\ulam{x}{t}} &= \mathsf{acc}[\ldots,\ \mathsf{Hashed}\;\uhash{\mathsf{R}(x)\cdot\HEnv}{t}]\\
  \uhash{\HEnv}{\uapp{t}{u}} &= \mathsf{acc}[\ldots,\ \mathsf{Hashed}\;\uhash{\HEnv}{t},\ \mathsf{Hashed}\;\uhash{\HEnv}{u}]
\end{align*}
and correspondingly at the other formers. Three things are load-bearing. Binder \emph{names are
discarded} on the way in, so $\alpha$-equivalent terms hash equally. \emph{Annotations are excluded
by construction} --- ``these should never affect the meaning of the term'' \src{ABT.hs:136-137}. And
a variable bound by a cycle frame $\mathsf{L}(V)$ hashes to the frame's index, \emph{the same index
for every member of $V$}: that is what \cref{def:comphash} exploits. A free variable is an error.
\end{definition}

\begin{definition}[The type is inside the term hash]\label{def:typeinhash}
\src{Hashing/V2/Term.hs:92-109} Before hashing, each member of a binding group is wrapped in its
type: $t \mapsto \uann{t}{T}$, replacing an existing top annotation if present. So the hash of a
definition is a function of its type as well as its body.
\end{definition}

\begin{remark}[Type-in-hash versus $\TyOf$]\label{rem:typeinhash}
A signature change \emph{is} an identity change, so a cached type can never be stale and
\textsc{U-Ref} may read $\Delta$ without a derivation (\cref{rem:uref-delta}). \arborstlc{} instead
makes the type an observational aspect $\TyOf$ \emph{about} a hash. That reads as the obvious choice
and is not: it is the choice a permissive store forces, since only an aspect can be absent, partial,
or record that a term is ill-typed --- which is what the holes line needs. Unison's store admits no
ill-typed definition, so it can afford the stronger identity. There is a
\texttt{hashTermComponentsWithoutTypes} \src{Term.hs:120-122} used where no type is available, which
is the exception proving the rule.
\end{remark}

\subsection{Reference transparency, and its boundary}

\begin{proposition}[Transparency holds exactly at position $0$]\label{prop:transparent}
\src{Hashing/V2/Term.hs:135-146} In the term layer,
\[
  \uhash{\HEnv}{\uref{\UDer{h}{0}}} = h,
  \qquad
  \uhash{\HEnv}{\uref{\UDer{h}{i}}} = \mathsf{acc}[\mathsf{Tag}\;1,\ \mathsf{Hashed}\;h,\ \mathsf{Nat}\;i]
  \quad (i \neq 0).
\]
\end{proposition}

\begin{remark}[Two consequences, and one correction]\label{rem:transparent}
For $i = 0$ --- every non-recursive definition, and the head member of a cycle --- a reference
contributes \emph{literally} the referent's hash. Hence: a definition whose whole body is a bare
reference \emph{is} its referent ($x = 1+1$ and $y = x$ hash the same, as the source comment says);
and \emph{inlining is hash-preserving}, since a reference already contributes exactly what the
inlined body would.

For $i \neq 0$ it is opaque, tagged with the position. So transparency and the component model are
not independent features: the boundary between them falls at $\Pos = 0$.

\texttt{docs/systems/unison/02-store-and-hashing.md} states transparency flatly, ``at any
position''. That is true of the position \emph{within the parent term} and false of the position
\emph{within the component}; corrected there.

\textbf{Branch note.} arbor's own position on this axis is in flux at the time of writing.
\coreref{def:node} carries an opaque $\nRef{h}$, and this document sits beside that. A substrate
decision to adopt transparency was taken on 2026-08-24 and mechanized, but on the
\texttt{reference-transparency} branch, not here; if it lands, this ceases to be a fork between the
two systems --- \emph{except} for the positional asymmetry above, which arbor has no analogue of
either way, because it has no components.
\end{remark}

\subsection{Component hashing}

This is the deepest mechanism in the document, and the one whose properties are least obvious.

\begin{definition}[Component hashing]\label{def:comphash}
\src{Hashing/V2/ABT.hs:73-100, 175-217} Let $C = \langle (y_1,u_1),\dots,(y_k,u_k)\rangle$ be a
component, \emph{listed in name order} (the implementation always obtains it as
$\mathsf{Map.toList}$). Let $V = \{y_1,\dots,y_k\}$.

\emph{Step 1 --- permutation hashes.} In the environment $\HEnv_p = \mathsf{L}(V)$, every intra-cycle
reference resolves to the same index, so member bodies become comparable without any of them yet
having an identity:
\[
  \phash{y_j} \;=\; \uhash{\HEnv_p}{u_j}.
\]

\emph{Step 2 --- the binding order.} Sort the members by $\phash{\cdot}$, \textbf{stably}, giving a
permutation $\pi$; set $\HEnv = \mathsf{R}(y_{\pi(1)})\cdots\mathsf{R}(y_{\pi(k)})$. Each member now
has a distinct de Bruijn index, and the member hashes are
$h_j = \uhash{\HEnv}{u_{\pi(j)}}$.

\emph{Step 3 --- the storage order.} With
$\overline{\tau} = \mathsf{Tag}\;1,\ \mathsf{Hashed}\;h_1,\dots,\mathsf{Hashed}\;h_k$ shared by every
member, put
\[
  \nhash{y} \;=\; \mathsf{acc}\bigl(\overline{\tau} \;+\!\!+\; [\mathsf{Hashed}\;\uhash{\HEnv}{\uvar{y}}]\bigr),
\]
so a member is disambiguated \emph{only} by its own index in $\HEnv$. Sort the members by
$\nhash{\cdot}$; that order is the component's storage order, position $i$ in $\UDer{h}{i}$ counts in
it, and
\[
  \comphash(C) \;=\; \mathsf{acc}[\mathsf{Hashed}\;\nhash{y_{\sigma(1)}},\dots,\mathsf{Hashed}\;\nhash{y_{\sigma(k)}}]
\]
for $\sigma$ the sorting permutation.
\end{definition}

\begin{remark}[Two orders, not one]\label{rem:twoorders}
$\pi$ and $\sigma$ are different permutations of the same component. $\pi$ fixes the de Bruijn
indices used \emph{while hashing} member bodies; $\sigma$ fixes the $\Pos$ indices used \emph{in
stored references}. They coincide only by accident, since $\sigma$ sorts by a hash of the $\pi$-index.
Nothing observable depends on the difference --- re-hashing re-derives $\HEnv$ --- but a
reimplementation that conflated them would produce different hashes, and no prose description of the
algorithm mentions it.
\end{remark}

\begin{definition}[Ingest]\label{def:uingest}
\src{Hashing/V2/ABT.hs:106-134} $\hashcomps(\bg)$ decomposes $\bg$ into strongly connected components
in topological order and folds \cref{def:comphash} over them, substituting $\UDer{h}{i}$ for the
names of already-hashed components before hashing the next. The store is extended by each component
at its hash.
\end{definition}

\subsection{What component hashing guarantees}

\begin{theorem}[Conditional presentation-independence]\label{thm:ordering}
Let $C$ and $C'$ be the same component listed in two different orders.
\begin{enumerate}[nosep,label=(\alph*)]
  \item If $\phash{\cdot}$ is \emph{injective} on $V$, then $\comphash(C) = \comphash(C')$, the member
        hashes agree, and each member receives the same $\Pos$.
  \item If $\phash{\cdot}$ is not injective, $\comphash$ depends on the listed order. Since the list
        is always obtained in name order, the component's hash --- and every reference into it ---
        depends on the members' \textbf{names}.
\end{enumerate}
\end{theorem}
\begin{proof}[Proof sketch]
$\HEnv_p$ mentions no member individually, so $\phash{y}$ is a function of $u_y$ alone and is
unaffected by the listing. (a) If $\phash{\cdot}$ is injective, sorting by it is a total order on $V$
determined by the members' bodies, so $\pi$, hence $\HEnv$, hence every $h_j$, hence every
$\nhash{\cdot}$, hence $\sigma$ and $\comphash$, are all listing-independent. (b) If
$\phash{y} = \phash{y'}$ for $y \neq y'$, the sort in Step 2 is stable and therefore returns them in
listed order; exchanging them in the listing exchanges their de Bruijn indices, which changes
$\nhash{\cdot}$ and in general $\comphash$.
\end{proof}

\begin{corollary}[The side condition is decidable, and is checked]\label{cor:detect}
\src{ABT.hs:186-192, 208-217} Injectivity of $\phash{\cdot}$ on $V$ is decided by grouping the
members by permutation hash. \texttt{doHashCycle} does exactly this and emits
\texttt{IncompleteElementOrderingError} listing the structurally equivalent sets.
\end{corollary}

\begin{remark}[Total function, conditional guarantee, aborting implementation]\label{rem:notpartial}
It is tempting --- and \texttt{docs/systems/unison/02-store-and-hashing.md} does it --- to say that
canonical ordering ``is partial'' and that Unison ``refuses''. Both are slightly wrong, and the
precise version is more interesting.

$\comphash$ is a \emph{total} function: on the ambiguous input it returns a hash. What fails is not
definedness but \emph{presentation-independence} --- the property content addressing exists to
provide. The fallback is alphabetical order of user-chosen names, which is precisely the kind of
dependency the whole design is meant to eliminate.

The implementation's response is at the \emph{caller}. \texttt{doHashCycle} returns the condition as a
warning and its own comment says ``hashing always succeeds even if it generates warnings'';
\texttt{crashOnHashingWarning} then turns it into an exception, and the main term-component path takes
that route \src{UnisonFile.hs:284}, with a top-level handler rendering it as bug \texttt{E253299} plus
the workaround --- add a dummy binding such as \texttt{\_ = "this is the foo definition"}
\src{ABT.hs:55-62; Main.hs:116}. Internal \texttt{let rec} bindings deliberately ignore the warning,
because there the ordering is not observable \src{ABT.hs:167-172}.

So the honest statement is: \emph{a decidable side condition guards presentation-independence, and
the implementation aborts rather than store a hash that violates it.} That is a stronger and more
defensible engineering position than ``it is partial'', and it is a sharper problem for a formalism,
because the side condition has to appear in the statement of every downstream theorem.
\end{remark}

\begin{theorem}[Hashing collapses $\alpha$-equivalence and cycle permutation]\label{thm:ualpha}
Let $\phash{\cdot}$ be injective on $V$. Then $\comphash$ identifies two components exactly when they
are related by $\alpha$-equivalence of members (\cref{def:ualpha}) together with a permutation of the
cycle. It does not identify observationally equivalent members.
\end{theorem}
\begin{proof}[Proof sketch]
$(\Leftarrow)$ Binder names are discarded by \cref{def:uhash} and permutation-independence is
\cref{thm:ordering}(a). $(\Rightarrow)$ By injectivity of $\mathsf{acc}$ on token streams and the
domain-separating tags of \cref{def:tokens}, downward through the structure, as in
\coreref{thm:alpha}.
\end{proof}

\begin{remark}[Against \coreref{thm:alpha}]\label{rem:alphacontrast}
\coreref{thm:alpha} is unconditional and its equivalence is $\alpha$ alone. Here the equivalence is
coarser --- it includes cycle permutation --- and the theorem is \emph{guarded}. Both differences
come from the same source, which is that the unit of hashing is a component rather than a node.
\end{remark}

\section{Part III --- Naming}\label{sec:unaming}

\begin{definition}[Namespace]\label{def:unames}
\src{Hashing/V2/Branch.hs:22-39; sql/create.sql:271} A namespace is a \emph{relation}
\[
  \UNames \;\subseteq\; \Name \times \Referent ,
\]
written $\UNames(x)$ for $\{\,\varrho \mid (x,\varrho) \in \UNames\,\}$. One name may denote several
referents and one referent may have several names; both are ordinary states, not errors. The
database agrees: the name-lookup key includes the referent columns, so several rows per name are
legal.
\end{definition}

\begin{definition}[Unconflictedness]\label{def:unconf}
\src{Branch/Type.hs:113-119, 291-314} $\unconf{\UNames}{x}$ holds iff $|\UNames(x)| = 1$;
$\unconf{\UNames}{}$ holds iff it holds at every name in $\dom(\UNames)$. When it does, $\UNames$
determines a partial function and we write $\uresolve{\UNames}{x}{\varrho}$.
\end{definition}

\begin{remark}[Conflict is representable; operations demand its absence]\label{rem:conflict}
This is the shape \texttt{feedback\_visible\_breakage} describes --- commit and report, do not gate ---
applied to names. But note where the cost lands: \texttt{update} cannot proceed against a conflicted
namespace and \emph{asserts} unconflictedness before doing anything \src{Update2.hs:99-102}, and
unconflictedness is recomputed as a derived view. So the representable state is refused by the
operations that matter, and Unison's own forward-looking \texttt{BranchV3} format removes conflicted
names outright \src{U/Codebase/BranchV3.hs:16-30}.

\coreref{def:ns} makes $\Names$ a partial function, so \cref{def:unconf} holds by construction and
\cref{def:unames}'s generality is unavailable. arbor's position (2026-08-20) is that multiplicity
belongs to a \emph{family} of namespaces rather than to a binding. The two data points above weigh
for that reading rather than against it.
\end{remark}

\section{Part IV --- The evaluation cache}\label{sec:ucache}

\begin{definition}[Watch cache]\label{def:watch}
The cache is a finite partial function $\UCache : \Hash \pfn \Hash$, from the hash of an expression to
the hash of its value. Both are store hashes.
\end{definition}

\begin{remark}[The key need not be a definition]\label{rem:watchkey}
$\dom(\UCache)$ is the hash of an \emph{expression}, which need not be named and need not be a member
of any component the user declared. \coreref{rem:nosort} arrives at the same place from the other
direction --- arbor's store carries no definition sort, so ``definition-hood'' is conferred by naming
and the cache can be keyed by any hash. Two systems, independently, decline to make ``is a
definition'' a property of stored data.
\end{remark}

\begin{theorem}[Cache soundness is stable under growth]\label{thm:wstable}
If $\UCache(h) = h_v$ is sound in $\UStore$ and $\UStore \subseteq \UStore'$, it is sound in
$\UStore'$.
\end{theorem}
\begin{proof}[Proof sketch]
Evaluation of $h$ reads only entries reachable from $h$; all of them are in $\dom(\UStore)$ and, by
immutability, identical in $\UStore'$. Exactly \coreref{thm:stability}'s argument, and it uses
neither well-formedness nor anything about the namespace.
\end{proof}

\begin{corollary}[No invalidation is needed]\label{cor:wnoinval}
An entry, once written, is valid in every future store. Consequently no invalidation logic is
required --- and none exists: the only eviction paths in the implementation are a debug-only
wholesale delete and a garbage collection of orphaned hashes, verified by absence over the codebase.
\end{corollary}

\begin{remark}[Where this differs from \coreref{cor:cache}, and where it does not]\label{rem:cachesame}
It does not differ. This is the one part of the design the two systems agree on completely, down to
the argument. It is worth stating precisely because it is the claim Unison is best known for and has
never written down: ``never invalidated'' is not a heuristic about how often definitions change, it is
a consequence of immutability plus the cache being keyed by a hash of what was evaluated.
\end{remark}

\section{Part V --- Update}\label{sec:uupdate}

\subsection{Dependents}

\begin{definition}[Dependents]\label{def:dependents}
$\deps(h,i)$ is the set of references occurring in the $i$-th member of the component at $h$;
$\dependents$ is its converse, maintained as an index populated when a definition is saved. Note
that this index exists \emph{because} a reference is a stored node even though it hashes
transparently at position $0$ (\cref{prop:transparent}): transparency is a property of the hash, not
of the representation.
\end{definition}

\begin{definition}[Update scope]\label{def:uscope}
\src{Operations.hs:1125-1126; Update2.hs:139-179} Given a set $Q$ of references being updated and a
namespace $\UNames$,
\[
  \tdeps(Q) \;=\; \bigl(\dependents^{+}(Q) \;\cap\; \mathcal{S}\bigr) \setminus (F \cup L)
\]
where $\dependents^{+}$ is the transitive closure excluding self-references, $\mathcal{S}$ is the set
of references having an \emph{unconflicted} name in $\UNames$, $F$ is what the incoming file itself
shadows, and $L$ is everything under $\lib$.
\end{definition}

\begin{remark}[Naming is what puts a definition in scope]\label{rem:scopenaming}
An unnamed definition is not a dependent to be updated, even if it references the target. That is the
no-definition-sort stance doing load-bearing work in a second system: naming is the only thing that
makes a stored object a participant. Note also what is \emph{absent} --- there is no type-based
gating. Unison used to classify each edit as $\mathsf{Same} \mid \mathsf{Subtype} \mid
\mathsf{Different}$ and propagate only the first two; that machinery was deleted in 2025. The current
design computes the closure and lets the typechecker decide.
\end{remark}

\subsection{Update, as rendering}

\begin{definition}[Pretty-print environment]\label{def:ppe}
\src{Update2.hs:429-443} A $\ppe$ assigns each reference a name to render it by, under two different
suffixification strategies: definitions \emph{in the file} are suffixified by name, definitions
\emph{in the codebase} by hash. The asymmetry is forced --- aliases sharing a suffix may be referred
to by that suffix in the codebase but not in a file, where the parser reports an ambiguity.
\end{definition}

\begin{definition}[Update]\label{def:update}
\src{Update2.hs:89-258} Given a typechecked incoming file $F$ and a configuration
$\UConfig{\UStore}{\UNames}{\UCache}$ with $\unconf{\UNames}{}$:
\begin{enumerate}[nosep,label=\arabic*.]
  \item Let $Q$ be the references of the names $F$ redefines, and $D = \tdeps(Q)$.
  \item Render: $S = \render(\ppe, D)$, source text for every dependent.
  \item Parse and typecheck $F \cup S$ \emph{as one file}.
  \item If it typechecks, ingest (\cref{def:uingest}) and rebind every affected name.
  \item If it does not, \textbf{remove} the offending definitions' names from $\UNames$ and deliver
        $S$ to the user as editable source on a dedicated update branch.
\end{enumerate}
\end{definition}

\begin{remark}[The residual, rendered]\label{rem:residual}
Step 5 is the sharpest single contrast in this document. \stlcref{def:residual} has migration commit
and report a residual \emph{set of names}; \texttt{update} evicts the broken definitions from the
namespace and hands back \emph{the code itself}, so the namespace stays coherent and the broken work
becomes a scratch file. The residual is not an error report, it is the next thing to edit. Note that
this requires \cref{rem:names}: what is handed back must be readable, so binder names must have
survived storage.
\end{remark}

\begin{proposition}[Update propagates by exactly one strategy]\label{prop:follow-only}
The transition of \cref{def:update} admits no parameter controlling propagation: $\tdeps$ is fixed.
In the vocabulary of \texttt{docs/design/04-naming-layer.md} it is $\Follow$ with scope fixed at the
whole namespace. There is no $\Pin$ --- the nearest analogue is declining to run \texttt{update} ---
and no $\Explicit$ at selection time, though something like it reappears at failure time, since what
fails to typecheck comes back as source for the user to edit.
\end{proposition}

\subsection{The obligation update rests on}

\begin{proposition}[Update is correct only if printing inverts parsing]\label{prop:print-parse}
Let $d$ be a dependent not redefined by $F$, and let $d'$ be the definition obtained from step 4 for
$d$. The intended semantics of \cref{def:update} is that $d'$ differs from $d$ \emph{only} by having
its references to $Q$ replaced by their new targets. This holds iff, for every $d \in D$,
\[
  \uparse(\ppe,\ \render(\ppe, d)) \;=\; d
  \qquad\text{modulo exactly that replacement.}
\]
\end{proposition}
\begin{proof}[Proof sketch]
Step 3 reconstructs $d'$ from text alone. Any discrepancy introduced by the round trip --- a binder
renamed so as to change capture, an identifier resolving to a different alias, a different
associativity --- is preserved into $d'$ and changes its hash for a reason unrelated to the update.
Conversely if the round trip is exact except at the references being retargeted, $d'$ is by
construction the intended substitution.
\end{proof}

\begin{remark}[Unison does not state this; arbor proves it]\label{rem:printparse}
The implementation's own comment for this step is: \emph{``We are updating old references to new
references by rendering old references as names that are then parsed back to resolve to new
references (the world's weirdest implementation of AST substitution)''} \src{Update2.hs:424-427}.
The correctness property that comment presupposes appears nowhere in the source. It is instead
\emph{tested}: \texttt{unison-src/transcripts-round-trip/} renders a regression corpus, re-adds it to
a fresh namespace, and asserts the namespace diff is empty. The corpus file is named
\texttt{reparses-with-same-hash.u}, and its sibling \texttt{reparses.u} holds the weaker cases that
need only parse. The naming is the tell: the property is understood precisely and lives in a golden
file.

\coreref{prop:print-elab} is that property, stated and proved --- and stated at the right generality,
since printing is modeled as a \emph{judgment} so the theorem quantifies over every rendering the
printer might choose. Two caveats belong with any use of this comparison. First, \arborcore{}'s
proposition is about \arborcore{}'s languages, not Unison's, which are vastly larger; this is an
argument about the \emph{shape} of the guarantee, not a theorem about Unison. Second, \arborcore{}'s
own migration is a structural rewrite over stored nodes that needs no round-trip lemma at all --- so
arbor proves something it does not itself depend on, and Unison depends on something it does not
prove.
\end{remark}

\subsection*{What the comparison is good for}

Two claims survive it. The first is a positioning claim and it is narrow enough to defend: the
closest comparable system has a load-bearing correctness property maintained by a regression corpus,
and arbor has the theorem in the same shape. That is better than ``first formal treatment'' because
it names a mechanism.

The second is methodological. Three of this document's results --- the $\Pos = 0$ boundary of
transparency (\cref{prop:transparent}), the two orderings inside component hashing
(\cref{rem:twoorders}), and the fact that ordering ambiguity yields a \emph{name-dependent hash}
rather than a failure (\cref{rem:notpartial}) --- were not visible in a careful prose read of the same
source, and two of them correct that read. Formalizing another system's design is a way of reading
it, and it finds different things than reading it as prose does.
